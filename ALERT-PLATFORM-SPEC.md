## 1. Контекст и ограничения

### 1.1. Задача

Крупное промышленное предприятие использует 7 систем мониторинга, генерирующих 5400 событий в сутки в разных форматах. 65% уведомлений закрываются инженерами без реакции в первые 2 минуты. Среднее время незамеченного простоя критичного сервиса — 14 минут, что оценивается в 3,2 млн рублей упущенной выгоды за инцидент. Ручная обработка алертов первой линией — 48 человеко-часов в сутки.

Требуется единая платформа приёма, обработки и адресной доставки оповещений.

### 1.2. Жёсткие ограничения

| Ограничение | Следствие для архитектуры |
|---|---|
| Единственный обязательный канал доставки — TrueConf | Собственный клиент не разрабатывается. Всё взаимодействие с сотрудником — через бота и веб-кабинет |
| Импортозамещение | Отсутствие зависимости от зарубежных вендоров и облачных сервисов. Подробнее — 1.4 |
| Запрет передачи данных во внешние облака | Все модели работают в контуре предприятия |
| Исторические данные для обучения недоступны | Корреляция строится на конфигурации, а не на обучении |
| Реальные примеры алертов заказчиком не предоставлены | Датасет генерируется синтетически, методика — раздел 18 |
| Пилот: Блок разведки и добычи, Zabbix + SolarWinds, 4 филиала, 87 пользователей | Демонстрация строится на этих двух источниках |
| Целевой MTTR ≤ 20 минут, доля ложных срабатываний ≤ 5% | Метрики выносятся на дашборд как контролируемые |

### 1.3. Отвергнутые подходы

| Подход | Причина отказа |
|---|---|
| Редактирование уже отправленного уведомления по мере развития инцидента | Доставленное сообщение — совершившийся факт, на который человек мог отреагировать. Отменять его задним числом недопустимо |
| Предварительное описание всех причинно-следственных связей между алертами | Если заказчик способен описать связи заранее, платформа ему не нужна |
| Обучение модели корреляции на исторических логах как ядро | Данные недоступны; в производственных экспериментах заказчика сходимость метода составила менее 9% |
| Собственное приложение для сотрудников | TrueConf уже развёрнут, не требует установки, обучения и отдельной поддержки |
| Вывод графа зависимостей из рунбуков | Инструкция описывает последовательность проверки, а не состояние графа |
| Автоматическое подавление алертов решением системы | Заменено на управляемые пользователем режимы подписки |

### 1.4. Принцип выбора программного обеспечения

Требование импортозамещения трактуется не как «каждая библиотека должна быть в реестре отечественного ПО» — такая трактовка нереализуема: язык программирования, веб-фреймворк, библиотека отрисовки графов и драйвер базы данных в реестре отсутствуют и присутствовать не могут. Значимо другое: **отсутствие санкционного и лицензионного риска и отсутствие зависимости от зарубежных облаков и вендорской поддержки.**

Стек делится на три категории:

| Категория | Требование | Примеры в решении |
|---|---|---|
| **Инфраструктурные продукты** — операционная система, СУБД, брокер сообщений, оркестрация, хранилище секретов | предпочтительно реестр отечественного ПО; заменяемость обязательна | Astra Linux, Postgres Pro, Arenadata Streaming, Deckhouse, Tarantool |
| **Открытые компоненты без вендора** — язык, фреймворки, библиотеки | свободная лицензия (MIT, Apache 2.0, BSD, PSF), развёртывание внутри контура, работоспособность без обращений к внешним сервисам | Python, FastAPI, SQLAlchemy, networkx, matplotlib, `python-trueconf-bot` |
| **Проприетарные зарубежные продукты и облачные сервисы** | не используются | — |

Ключевой аргумент для защиты решения: инфраструктурный слой построен на продуктах из реестра и заменяем без переписывания кода, а прикладной слой — на свободном ПО, которое работает в закрытом контуре и не создаёт зависимости от иностранного поставщика. Библиотека взаимодействия с TrueConf разрабатывается самим вендором мессенджера, что снимает вопрос о поддержке интеграционного слоя.

Отдельная оговорка по моделям: используются открытые веса, разворачиваемые локально. Обращения к внешним API языковых моделей отсутствуют в принципе — это требование политики информационной безопасности, а не предпочтение.

## 2. Инварианты

Пять правил, которые не нарушаются ни при каких обстоятельствах.

**И1. Неизменяемость доставленного.** Отправленное уведомление об инциденте не редактируется и не удаляется. Развитие инцидента передаётся новыми сообщениями с явной типизацией. Исключения перечислены в 9.7 и касаются только служебных сообщений бота, не являющихся уведомлениями.

**И2. Неизменяемость оригинала.** Текст алерта из источника доставляется дословно, в выделенной зоне сообщения. Платформа добавляет обвязку сверху и снизу, но не перефразирует.

**И3. Ненулевая доставка.** Ничто не исчезает бесследно. Свёрнутое извлекается в один шаг и разворачивается автоматически по сторожевому таймеру.

**И4. Объяснимость.** У каждого уведомления и у каждого отсутствия уведомления есть трассировка: источник → парсер → объект → сервис → правило → приоритет → адресат → канал.

**И5. Деградация в сторону шума.** Отказ любого интеллектуального компонента приводит к доставке сырого алерта, а не к молчанию.

## 3. Каноническая модель данных

### 3.1. Почему нужна нормализация терминов

| Система | Что отправляет | Природа |
|---|---|---|
| Zabbix | `event` — смена состояния триггера, `problem` — открытое состояние, `alert` — попытка доставки | фронт + состояние |
| Prometheus / Alertmanager | `alert` в статусе firing, повторяется, пока активен | уровень через повторы |
| SolarWinds | `alert` с trigger/reset | фронт с явным сбросом |
| Tibbo AggreGate, Saymon | смена состояния объекта по опросу | уровень |

Без разделения этих сущностей метрики MTTR недостоверны, дедупликация не работает, корреляция даёт ложные связи.

### 3.2. Пять слоёв

```
Сигнал → Событие → Проблема → Инцидент → Уведомление
```

| Слой | Определение | Изменяемость | Ключевые поля |
|---|---|---|---|
| `Signal` | сырая полезная нагрузка как пришла | неизменяем, WORM | `id`, `source_id`, `received_at`, `raw_body`, `hash` |
| `Event` | нормализованный факт перехода состояния | append-only | `id`, `signal_id`, `dedup_key`, `state`, `occurred_at`, `ingest_ts`, `symptom_class` |
| `Problem` | состояние с жизненным циклом и длительностью | мутабельна | `id`, `dedup_key`, `status`, `opened_at`, `resolved_at`, `object_id`, `component` |
| `Incident` | кластер проблем с одной первопричиной | мутабелен | `id` (INC-XXXX), `root_problem_id`, `symptom_problem_ids`, `priority`, `services` |
| `Notification` | акт доставки конкретному человеку | мутабелен по статусу | `id`, `incident_id`, `user_id`, `chat_id`, `message_id`, `type`, `status` |

Состояния `Problem`:

```
OPEN → ACKNOWLEDGED → RESOLVED
  ↓          ↓
FLAPPING  SUPPRESSED
```

Поле `Notification.message_id` — критическое. Оно возвращается методом отправки и служит ключом для сопоставления входящих ответов пользователя с инцидентом (см. 9.4).

### 3.3. Типы сообщений

| Тип | Условие отправки |
|---|---|
| `NEW` | первое событие инцидента |
| `SUPPLEMENT` | определена первопричина, добавлены связанные, изменился охват сервисов |
| `REPEAT` | событие повторилось, инцидент активен |
| `ESCALATION` | не подтверждено в срок SLA |
| `CLOSURE` | восстановление |

Дисциплина: не более трёх `SUPPLEMENT` на инцидент; далее только `ESCALATION` и `CLOSURE`. Дополнение отправляется только при существенном изменении — смена первопричины, новый затронутый сервис, изменение приоритета.

## 4. Идентификация объекта

### 4.1. Объект и компонент

Диск C: существует на каждой виртуальной машине. Корреляция всех алертов по диску C: с разных серверов бессмысленна. Поэтому:

- **Объект** — сущность с уникальным идентификатором: IP, FQDN, инвентарный или серийный номер.
- **Компонент** — часть объекта, уникальная только внутри него: диск, интерфейс, процесс, служба.

```
dedup_key = sha256(site | object_id | component | symptom_class)
```

Идентификатор источника в ключ не входит: Zabbix и SolarWinds, наблюдающие один коммутатор, должны схлопнуться в одну проблему.

**Правило валидации:** правило корреляции, использующее компонент без объекта, не сохраняется.

### 4.2. Владение

У объекта может быть **несколько** компаний-владельцев (дочерних обществ). Это нормальное состояние данных.

```
Объект ──< Владение >── Дочернее общество
   │
   └──< Обслуживает >── Сервис ──< Ответственность >── Роль → Сотрудник
```

Следствие: уведомление может уходить в несколько зон ответственности, но действует дедупликация на человека — один сотрудник получает одно сообщение по инциденту независимо от числа затронутых его сервисов.

### 4.3. Резолвер

Каскад сопоставления события с объектом:

1. точный ключ из словаря подтверждённых алиасов;
2. нормализованный FQDN;
3. IP + временное окно с учётом аренды DHCP;
4. MAC, серийный или инвентарный номер;
5. нечёткое сравнение имени;
6. **карантин** — событие доставляется по резервному правилу «источник → дежурная группа», помечается как нерезолвленное, попадает в очередь администратора для создания постоянного алиаса.

Метрика `ci_resolution_coverage` выносится на дашборд.

## 5. Конвейер обработки

```
Источники → [0] Шлюз → [1] Парсер → [2] Резолвер → [3] Состояния
          → [4] Коррелятор → [5] Приоритет → [6] Маршрутизатор
          → [7] Доставка TrueConf → [8] Обратная связь → (в [4])
```

### Стадия 0. Шлюз приёма

Протоколы: HTTP webhook, syslog, SNMP trap, AMQP, SMTP, опрос по API. Логика: аутентификация, ограничение частоты, проверка размера, запись сырого сигнала в WORM, публикация в очередь, немедленное подтверждение источнику. Парсинг здесь не выполняется — при отказе конвейера события копятся, источник не теряет данные.

### Стадия 1. Парсер

Парсер — версионируемое YAML-описание, не код. Селекторы (JSONPath, регулярные выражения), карта соответствия severity, шаблон `dedup_key`, извлечение идентификаторов объекта. Тестируется в песочнице, публикуется через админку. Это механизм подключения источников без изменения ядра.

**Детектор дрейфа схемы.** Отслеживается `parse_success_rate` в скользящем окне. Падение более 5% → инцидент на платформу, автоматический откат версии парсера, непарсящиеся сигналы в резервный канал в исходном виде.

### Стадия 2. Резолвер

См. раздел 4.3. Обогащает событие: площадка, подсеть, дочернее общество, сервис, критичность, владельцы, активное окно плановых работ, версия установленного ПО.

### Стадия 3. Менеджер состояний

Свёртка событий в проблемы по `dedup_key`, схлопывание повторов, гистерезис.

**Цикл сверки.** Раз в 1–5 минут платформа опрашивает источник (`problem.get` в Zabbix, `/api/v2/alerts` в Alertmanager) и сравнивает свой набор активных проблем с фактическим. Расхождения закрываются с признаком `closed_by_reconciliation` — отдельным флагом, чтобы не искажать MTTR. Для источников без доступного API либо с односторонним трафиком — TTL по классу симптома, что фиксируется в паспорте источника.

**Flapping.** При превышении порога переключений проблема переводится в `FLAPPING`, отправляется одно сообщение с счётчиком; дальнейшие переключения увеличивают счётчик без новых сообщений.

### Стадии 4–7

См. разделы 6, 7, 8, 9.

### Стадия 8. Обратная связь

Каждое действие получателя фиксируется как разметка и используется для предложения правил (раздел 10) и аналитики качества маршрутизации.

## 6. Корреляция

### 6.1. Принцип

Универсального алгоритма определения первопричины не существует: если отказала целая площадка, невозможно достоверно установить, пропало ли питание из-за отказа канала или наоборот. Поэтому ядро — **конструктор правил**, а не алгоритм. Ценность продукта в скорости настройки новой корреляции.

### 6.2. Оси корреляции

| Ось | Пример правила |
|---|---|
| Объект | диск, процессор и служба на одном сервере → один инцидент |
| Компонент | повторные срабатывания по одному интерфейсу |
| Топология | коммутатор недоступен → хосты за ним считать следствием |
| Подсеть | массовая недоступность в одном сегменте → сетевая проблема |
| Площадка | отказ по всей площадке → проверять питание и канал |
| Дочернее общество | сводка проблем по активу |
| Версия ПО, событие обновления | всплеск алертов на объектах, где вчера обновлён пакет |
| Окно плановых работ | алерты в окне помечаются как ожидаемые |
| Время | базовое условие любого правила |

### 6.3. Интеграция с управлением изменениями

Самый дешёвый по трудозатратам механизм снижения шума. Платформа получает календарь плановых работ: окно, объекты, ответственный. Алерты в окне не подавляются, а помечаются признаком «ожидаемое, работы CHG-882», направляются исполнителю работ вместо дежурной смены, при выходе за границы окна возвращаются в обычный режим.

### 6.4. Формат правила

```yaml
rule_id: corr-114
name: Недоступность хостов за коммутатором
when:
  trigger_symptom: host_unreachable
  cause_symptom: switch_port_down
  match: [subnet, site]
  window: 120s
then:
  mark_as: consequence
  root: cause_symptom
status: active          # draft | simulation | shadow | active | disabled
author: ivanov_ai
created_from: INC-4471
```

Жизненный цикл: `draft → simulation → shadow → active → disabled`.

**Симулятор.** Прогон по накопленной истории перед публикацией: «за 30 дней правило свернуло бы 412 алертов, из них 3 оказались самостоятельными инцидентами P1». Опасные правила не доходят до эксплуатации.

**Теневой режим.** Правило фиксирует, что сделало бы, не влияя на доставку.

### 6.5. Вспомогательные методы

Работают как советчики, предлагающие правила человеку, но не принимающие решений.

- **Топологический вывод** — если в CMDB есть граф зависимостей, платформа предлагает готовые правила по нему.
- **Семантическое сравнение** — один факт, описанный разными системами разными словами, выявляется по векторной близости при совпадении объекта и окна. Применяется для дедупликации, не для причинности.
- **Статистический анализ** — понижен до опционального, работает только на данных, накопленных самой платформой, выдаёт предложения с указанием поддержки и достоверности.

**Отдельный вывод.** Низкая сходимость исторического анализа означает, что инциденты не повторяются по одним причинам — признак работающего управления проблемами. Повторяемость поэтому вынесена не в модуль машинного обучения, а в **управленческий отчёт**: «сценарий повторился три раза по одной причине — вопрос к владельцу сервиса».

### 6.6. Окно корреляции

| Приоритет | Окно | Логика |
|---|---|---|
| P0 | 0 с | доставка немедленно, корреляция догоняет и отправляет `SUPPLEMENT` |
| P1 | 30 с | |
| P2–P3 | 90 с | размен задержки на снижение шума |

**Расхождение часов.** Хранятся `source_ts` и `ingest_ts`. Измеряется медианный дрейф каждого источника; при превышении порога упорядочивание переключается на `ingest_ts`, администратор получает предупреждение.

### 6.7. Защита от ошибок

- Кандидат в первопричину не подавляется никогда.
- **Сторожевой таймер:** если симптом свёрнут, а первопричина не закрыта в срок SLA, симптомы разворачиваются и эскалируются самостоятельно.
- Инженер может отменить связь одной командой; правило помечается спорным и уходит на пересмотр.

## 7. Приоритизация

Две независимые оси, сводимые явной матрицей.

- `technical_severity` (0–5) — нормализация из источника по таблице паспорта источника.
- `business_impact` (0–5) — критичность сервиса, зона и актив, время суток, идут ли работы, радиус поражения.

```
priority = matrix(technical_severity, business_impact) + modifiers
```

Модификаторы: повторяемость, ночное время, наличие подтверждённого дежурного, активное окно работ.

Матрица — таблица в админке, а не модель. Приоритет — зона ответственности бизнеса. Любое значение раскрывается до ячейки матрицы и применённых модификаторов.

## 8. Маршрутизация и подписки

### 8.1. Вычисляемая адресация

```
Адресаты = владельцы затронутых сервисов
         ∪ дежурные по расписанию
         ∪ ручные подписки (дельта)
         ∖ исключения (отпуск, делегирование, увольнение)
```

Подписка оформляется на роль или сервис, а не на источник событий. Ручные списки протухают — именно отсюда берётся сценарий «SMS на всю базу из 200 контактов».

### 8.2. Ре-аттестация

Раз в квартал владелец подтверждает состав получателей. Неподтверждённые подписки помечаются устаревшими. Сервисы без единого адресата выводятся отдельным отчётом и блокируют закрытие процедуры увольнения.

### 8.3. Режимы подписки

Решение о снижении шума принимает пользователь, а не система.

| Режим | Поведение |
|---|---|
| `instant` | каждое уведомление сразу |
| `digest` | сводка раз в N минут (15/30/60) |
| `on_demand` | только по команде боту |
| `critical_only` | P0–P1 сразу, остальное в дайджест |

P0 доставляется мгновенно всегда, независимо от режима и тихих часов.

### 8.4. Эскалация

Не прочитано за X минут → напоминание → резервный дежурный → руководитель смены → голосовой вызов для P0. Настраивается политикой на уровне сервиса.

## 9. TrueConf: реализация взаимодействия

### 9.1. Фактические возможности библиотеки

Библиотека `python-trueconf-bot`, Python 3.10+, установка `pip install python-trueconf-bot`. Транспорт — асинхронный WebSocket. Архитектура повторяет aiogram: `Router`, декораторы, magic-filter, middleware, FSM, шорткаты `message.answer()` и `message.reply()`.

Доступные методы, релевантные для платформы:

| Метод | Назначение | Применение у нас |
|---|---|---|
| `send_message(chat_id, text, parse_mode, reply_message_id)` | отправка текста | все типы уведомлений |
| `reply_message(chat_id, message_id, text, parse_mode)` | ответ на сообщение | ответ бота на команду в контексте инцидента |
| `edit_message(message_id, text, parse_mode)` | правка отправленного | только служебные сообщения, см. 9.7 |
| `remove_message(message_id, for_all)` | удаление | не используется |
| `forward_message(chat_id, message_id)` | пересылка | эскалация с сохранением оригинала |
| `send_photo(chat_id, file, preview, caption, parse_mode)` | изображение с превью | **граф инцидента** |
| `send_document(chat_id, file, caption, parse_mode)` | произвольный файл | выгрузка отчёта, сводки за период |
| `send_survey(chat_id, title, survey_campaign_id, ...)` | опрос | опционально, сбор обратной связи |
| `create_personal_chat(user_id)` | личный чат | идемпотентен: вернёт существующий |
| `create_group_chat(title)` / `create_channel(title)` | групповой чат и канал | **не идемпотентны**, см. 9.6 |
| `get_chats(count, page)` | список чатов | поиск существующего канала по названию |
| `get_chat_history(chat_id, count, from_message_id)` | история | восстановление контекста |
| `get_message_by_id(message_id)` | сообщение по идентификатору | трассировка |
| `add_participant_to_chat(chat_id, user_id, display_history)` | добавление в чат | управление составом каналов |
| `get_user_display_name(user_id)` | отображаемое имя | подстановка в тексты |
| `health_check()` / `on_health_check` | состояние соединения | самомониторинг платформы |

Форматирование: `parse_mode` принимает `TEXT`, `HTML`, `MARKDOWN`. Модуль `trueconf.utils.formatting` даёт классы `Bold`, `Italic`, `Underline`, `Strikethrough`, `Link`, `Mention`, `AllMention`, `Text` с методом `.as_html()`.

Ограничения: длина текстового сообщения — 4096 видимых символов, при превышении выбрасывается `TextMessageTooLongError`; для длинных текстов есть `trueconf.utils.safe_split_text`. Ограничения на файлы задаются администратором сервера и доступны через `bot.max_file_size`, `bot.file_extensions_list`, `bot.file_extension_filter_mode`.

Часть методов требует TrueConf Server 5.5.2+ или 5.5.3+ — версия развёрнутого сервера должна быть проверена до начала разработки.

### 9.2. Чего нет и как это обходится

**Inline-кнопок и callback-обработчиков в API нет.** Это принципиально меняет дизайн интерфейса бота по сравнению с телеграм-подобным.

Три механики замены, применяемые совместно:

| Замена | Как работает | Для чего |
|---|---|---|
| **Ответ на сообщение** | инженер отвечает на уведомление словом `взял`, `не мой`, `следствие INC-4470`; бот получает входящее сообщение и по идентификатору отвечаемого сообщения находит инцидент | быстрые действия по конкретному инциденту |
| **Текстовые команды** | `/сводка`, `/граф INC-4471`, `/связать INC-4471 INC-4470` | действия вне контекста конкретного уведомления |
| **Ссылки в HTML** | `Link("Взять в работу", url=".../inc/4471/ack?t=<токен>")` | действия, требующие формы или подтверждения; открываются в личном кабинете |

Ссылки несут одноразовый подписанный токен, привязанный к пользователю, инциденту и действию, со сроком жизни. Переход по ссылке не требует повторной аутентификации, но подтверждает личность.

Опция `send_survey` может использоваться для структурированной обратной связи («это шум? да / нет»), но требует заранее заведённой кампании опроса на стороне сервера, поэтому в базовый сценарий не входит.

### 9.3. Структура сообщения: конверт, а не письмо

Три зоны с разными правилами формирования:

| Зона | Содержимое | Кто формирует | Правило |
|---|---|---|---|
| Шапка | тип, приоритет, номер инцидента, объект, сервис | шаблон | без генеративных моделей |
| **Тело** | **оригинальный текст алерта** | источник | дословно, визуально отделено |
| Подвал | связанные, первопричина, действия, ссылки | правила + ИИ | пометка «гипотеза», всегда ниже оригинала |

Шаблон `NEW` (HTML):

```
🔴 <b>P0 · INC-4471</b> · Буровая №4 · БРД-Ноябрьск
─────── оригинал Zabbix ───────
PROBLEM: Well-4 PLC unreachable
(Trigger: ICMP ping failed x3)
───────────────────────────────
Сервис: АСУ ТП куста №4 · Критичность: высшая
Ответьте на это сообщение: <b>взял</b> · <b>не мой</b> · <b>следствие INC-XXXX</b>
<a href="...">Открыть карточку</a> · <a href="...">Граф инцидента</a>
```

Шаблон `SUPPLEMENT`:

```
🔵 <b>ДОПОЛНЕНИЕ к INC-4471</b>
Первопричина: коммутатор sw-brd-04, недоступен с 03:14:22
Связано алертов: 14 · Затронуто сервисов: 2
Основание: правило corr-114 (подсеть + окно 120 с)
<a href="...">Показать 14 связанных</a> · <a href="...">Отменить связь</a>
```

Шаблон `CLOSURE`:

```
🟢 <b>ЗАКРЫТО · INC-4471</b>
Восстановлено 03:41:08 · Длительность 26 мин
Подтвердил: Иванов А.И. в 03:16:44 (MTTA 2 мин 22 с)
Свёрнуто симптомов: 14 · <a href="...">Карточка</a>

Сообщения одного инцидента связываются через `reply_message_id`: каждое последующее отправляется ответом на первое. Это даёт визуальную группировку без поддержки тредов на стороне сервера.

### 9.4. Сопоставление ответа с инцидентом

Механизм, заменяющий кнопки. Последовательность:

1. При отправке уведомления метод возвращает объект ответа, содержащий идентификатор сообщения.
2. Идентификатор сохраняется: `notification.message_id → incident_id`.
3. Входящее сообщение от пользователя проверяется на наличие признака ответа на сообщение.
4. По идентификатору отвечаемого сообщения находится инцидент, действие применяется в его контексте.

```python
@router.message(F.text.lower().in_({"взял", "в работу", "ack"}))
async def on_ack(message: Message):
    incident = await store.incident_by_reply(message)   # см. раздел 19, п.1
    if incident is None:
        await message.answer("Не понял, к какому инциденту это относится. "
                             "Ответьте на уведомление или укажите номер: взял INC-4471")
        return
    await incidents.acknowledge(incident.id, user=message.author_id)
    await message.reply(f"Принято. INC-{incident.number} за вами.")
```

Резервный путь для случаев, когда ответ на сообщение недоступен: явное указание номера в тексте — `взял INC-4471`. Обработчик поддерживает обе формы.

### 9.5. Граф инцидента как изображение

Ключевой сценарий визуальной сводки. Кнопок нет, но есть отправка изображений с превью — граф отправляется картинкой.

**Что рисуем.** Направленный граф: узел-первопричина, узлы-симптомы, рёбра с подписью сработавшего правила. Цвет узла кодирует приоритет, форма — тип объекта, пунктир — связь с низкой уверенностью.

**Чем рисуем.** `networkx` для структуры, `matplotlib` для растеризации в PNG, либо `graphviz` при наличии в образе. Превью формируется уменьшением того же изображения.

```python
async def send_incident_graph(bot: Bot, chat_id: str, incident: Incident):
    png_path, preview_path = await render_incident_graph(incident)  # PNG + WebP превью
    caption = formatting.Text(
        formatting.Bold(f"Граф инцидента INC-{incident.number}"), "\n",
        f"Первопричина: {incident.root.title}\n",
        f"Симптомов: {len(incident.symptoms)} · Правил сработало: {incident.rules_fired}\n",
        formatting.Link("Открыть в кабинете", url=incident.web_url),
    )
    await bot.send_photo(
        chat_id=chat_id,
        file=FSInputFile(png_path),
        preview=FSInputFile(preview_path),
        caption=caption.as_html(),
        parse_mode=ParseMode.HTML,
    )
```

**Команды, порождающие граф:**

| Команда | Что рисуется |
|---|---|
| `/граф INC-4471` | граф конкретного инцидента |
| `/граф площадка БРД-Ноябрьск` | все активные инциденты площадки и их связи |
| `/граф сервис "АСУ ТП куста 4"` | цепочка влияния на сервис |
| `/граф смена` | сводный граф за смену: кластеры инцидентов и их размеры |

**Ограничения по размеру.** Перед отправкой проверяются `bot.max_file_size` и список разрешённых расширений — они задаются администратором сервера. При превышении граф упрощается: узлы схлопываются в агрегаты «12 хостов за sw-brd-04». Граф более чем на 40 узлов не рисуется целиком, вместо него отправляется агрегированная версия и ссылка на интерактивную в кабинете.

### 9.6. Каналы и получение chat_id

Существенная особенность: методы создания группового чата и канала **не идемпотентны** — повторный вызов с тем же названием создаёт ещё один чат. Создание личного чата, напротив, идемпотентно и вернёт существующий.

Отсюда правила:

1. `chat_id` каналов хранится в базе платформы, а не вычисляется каждый раз.
2. При старте выполняется сверка: перечисление доступных чатов постранично, поиск по названию, сопоставление с сохранёнными идентификаторами.
3. Создание канала — явная административная операция, не автоматическая.

Структура каналов:

| Канал | Назначение | Состав |
|---|---|---|
| Личный чат с ботом | адресные уведомления по подпискам | каждый сотрудник |
| Канал направления | инциденты по домену: сеть, АСУ ТП, Windows-инфраструктура | группа эксплуатации |
| Канал площадки | инциденты по дочернему обществу | руководство актива |
| Канал «полный поток» | все сырые алерты без фильтрации | дежурная смена, по желанию |

Канал «полный поток» существует ради доверия: он снимает возражение «а вдруг система проглотит важное». Падение его посещаемости — честный индикатор роста доверия к платформе.

### 9.7. Когда допустимо редактирование

Метод правки сообщения в API есть. Запрет на его использование — продуктовое решение, а не техническое ограничение, и он применяется выборочно.

| Тип сообщения | Правка |
|---|---|
| Уведомление об инциденте любого типа | **запрещена** (И1) |
| Служебное сообщение бота: «формирую граф…», «выполняю поиск…» | разрешена — заменяется результатом |
| Сообщение-дайджест в личном чате, ещё не прочитанное | разрешена — дайджест по определению агрегат, а не факт |
| Ответ бота на команду пользователя | разрешена |

Правило проверки: если сообщение может служить основанием для действия инженера и последующего разбора — оно не редактируется.

### 9.8. Надёжность доставки

WebSocket-соединение может разрываться; библиотека переподключается с ограничением числа попыток и максимальной задержкой. Из этого следуют требования к адаптеру:

1. **Исходящая очередь (outbox).** Уведомление сначала фиксируется в базе со статусом «в очереди», затем отправляется. Отправка без записи в очередь запрещена.
2. **Идемпотентность.** У каждого уведомления есть ключ идемпотентности; повторная отправка того же ключа не создаёт второе сообщение.
3. **Резервный путь.** При недоступности TrueConf дольше N минут P0 уходит альтернативным каналом, остальное копится с последующей досылкой и пометкой о задержке.
4. **Самомониторинг.** Обратный вызов состояния соединения и метод проверки состояния подключаются к внутреннему мониторингу платформы. Отказ бота не должен обнаруживаться по отсутствию алертов.
5. **Ограничение частоты.** Отправка сообщений не быстрее заданного порога, чтобы не упереться в ограничения сервера при шторме.

## 10. Ключевая функция: корреляция в один шаг

### 10.1. Постановка

Предварительное описание всех связей обесценивает платформу. Обучение на исторических логах недоступно и малорезультативно. Универсального алгоритма не существует. Остаётся четвёртый путь: **система учится от эксплуатации, в момент разбора инцидента.**

### 10.2. Сценарий в TrueConf

1. Инженер получает уведомление и видит, что это следствие другого инцидента.
2. Отвечает на уведомление: `следствие INC-4470` — либо, если номер неизвестен, просто `следствие`.
3. Во втором случае бот присылает пронумерованный список 3–4 кандидатов, ранжированных по близости во времени и числу совпавших признаков; инженер отвечает номером.
4. Платформа анализирует, **по каким осям совпали события**, и формулирует правило человеческим языком вместе с результатом симуляции.
5. Инженер отвечает `да` — правило активируется; `нет` — связывается только этот случай; игнорирует — не происходит ничего.

```
🧩 Предлагаю правило

Если «Хост недоступен» возникает на объектах той же
подсети в течение 120 с после «Порт коммутатора down»
— считать следствием.

Совпало признаков: подсеть, площадка, окно 40 с
За 30 дней сработало бы: 47 раз
Из них были самостоятельными инцидентами: 0

Ответьте: да — создать правило · нет — только этот случай
```

Диалог реализуется через машину состояний библиотеки: состояния `waiting_candidate → waiting_confirm`, с таймаутом и корректным выходом по любой другой команде.

### 10.3. Почему это снимает возражения

| Возражение | Ответ |
|---|---|
| «Если я могу описать связи заранее, зачем ваша система» | Мы не просим описывать заранее. Мы превращаем разовое действие в постоянное правило |
| Данных для обучения не дадут | Функция не требует корпоративных данных вообще |
| Универсального алгоритма нет | Мы даём инструмент, настраиваемый под площадку за минуты |
| Связи меняются вместе с инфраструктурой | Правило создаётся там, где изменение обнаруживается — в процессе разбора |
| Менять вид алертов рискованно | Функция ничего не меняет в теле алерта |

## 14. Безопасность и аналитика

### 14.1. Доступ

Интеграция с LDAP/AD, единый вход. Роли: сотрудник, владелец сервиса, дежурный, администратор маршрутизации, администратор источников, аудитор. Атрибутивное разграничение по площадке и дочернему обществу.

**Привязка учётной записи TrueConf.** Идентификатор пользователя мессенджера сопоставляется с учётной записью каталога при первом обращении к боту; сопоставление подтверждается через кабинет. Без подтверждённой привязки бот не выполняет действий, изменяющих состояние.

### 14.2. Жизненный цикл учётных записей

Удаление из группы каталога отключает подписки. Дополнительно: если уволенный был единственным адресатом сервиса, запускается проверка сервисов без адресата, эскалация руководителю и блокировка завершения процедуры до назначения преемника. Иначе возникает молчаливая зона.

### 14.3. Защита интеграций

Взаимная TLS-аутентификация, индивидуальный токен, подпись HMAC, список разрешённых адресов, валидация схемы, ограничение частоты. Для технологического сегмента — односторонняя передача, режим TTL вместо сверки. Токены действий в ссылках уведомлений одноразовые, подписанные, с ограниченным сроком жизни.

### 14.4. Данные и аудит

Сырые сигналы в WORM-хранилище с контролем целостности. Секреты в защищённом хранилище. Изменения правил, матриц и подписок версионируются с автором, временем и различиями. Журнал действий неизменяем.

### 14.5. Дашборд

| Группа | Метрики |
|---|---|
| Поток | событий в сутки по источникам, пики, распределение по приоритетам |
| Качество | `parse_success_rate`, `ci_resolution_coverage`, дрейф часов источников |
| Эффект | снижение шума, свёрнуто симптомов, сообщений на дежурного за смену |
| Доставка | доставлено, прочитано, подтверждено, эскалировано |
| Реакция | MTTA, MTTR по приоритетам и сервисам |
| Корреляция | активных правил, срабатываний, отменённых связей, точность |
| Платформа | доступность компонентов, задержка доставки, глубина очередей, состояние соединения бота |

Управленческие отчёты: повторяющиеся инциденты, гигиена алертов, молчаливые зоны.

## 15. Инфраструктура

### 15.1. Два стека

| Слой | Демонстрационный стенд | Целевой контур |
|---|---|---|
| Язык | Go для шлюза, pipeline, delivery planner и admin console; Python для TrueConf adapter, LDAP sweep и demo-runner | Python для vendor/служебных адаптеров, Go для конвейера и UI API; локальный ИИ вызывается по HTTP |
| API и воркеры | Go `net/http`/pgx + FastAPI для консоли | тот же контракт, с горизонтальным масштабированием worker |
| Очередь | PostgreSQL как очередь либо Redis Streams | Arenadata Streaming (Kafka) |
| Состояние проблем | PostgreSQL | Tarantool |
| Конфигурация, правила, аудит | PostgreSQL + pgvector | Postgres Pro + pgvector |
| Аналитика | PostgreSQL, материализованные представления | Arenadata QuickMarts |
| Архив сигналов | том на диске | S3-совместимое хранилище on-premise |
| Развёртывание | docker compose | Deckhouse Kubernetes на Astra Linux |
| Секреты | переменные окружения | Deckhouse Stronghold |

Переход на целевой стек выполняется поэтапно: шлюз, pipeline и delivery planner уже
перенесены на Go, а TrueConf оставлен за тонким Python-адаптером. Граница зафиксирована
версионированным контрактом и transactional outbox, поэтому admin/security API и
владение схемой можно переносить без остановки прототипа и без изменения канала.

Стек намеренно смешанный. Инфраструктурный слой целевого контура собран из продуктов реестра отечественного ПО и заменяем без переписывания прикладного кода: связь с ним идёт через стандартные протоколы — SQL, протокол Kafka, S3-совместимый интерфейс. Прикладной слой построен на свободном ПО с разрешительными лицензиями, работающем целиком внутри контура. Требование раздела 1.4 при этом выполняется: зависимости от зарубежных вендоров, облаков и платных лицензий в решении нет.

Заменяемость подтверждается на демонстрационном стенде: PostgreSQL заменяется на Postgres Pro сменой строки подключения, очередь на PostgreSQL — на Arenadata Streaming сменой реализации интерфейса очереди. Это заявляется как проверенное свойство архитектуры, а не как намерение.

### 15.2. Расчёт нагрузки

5400 событий в сутки — это 0,0625 события в секунду в среднем и 200–500 событий в минуту в пике аварии, то есть 3–8 в секунду. Требования к пропускной способности несущественны; определяющими являются задержка доставки, отказоустойчивость и способность поглотить всплеск.

**Вывод по смете.** При таком потоке вычисление векторных представлений полностью закрывается центральным процессором. Графические ускорители нужны только для дообучения и генерации сводок. Второй сервер с GPU из сметы может быть исключён — экономия порядка 200 тыс. рублей без потери функциональности.

### 15.3. Отказоустойчивость

Сервисы обработки без состояния, минимум по два экземпляра. Шлюз подтверждает приём до обработки. Целевые показатели: RTO 30 минут, RPO 0 для принятых сигналов — подтверждение источнику только после записи в архив и очередь.

### 17.3. Правила разработки

- Модель данных из раздела 3 — единственный источник истины; сущности не смешивать.
- Любая отправка в TrueConf идёт через outbox, прямых вызовов из бизнес-логики нет.
- Оригинальный текст алерта передаётся отдельным полем и никогда не проходит через шаблонизацию или модель.
- Каждое правило корреляции имеет автора, версию и возможность отката.
- Идентификаторы чатов и сообщений хранятся в базе, не вычисляются заново.
- Тесты обязательны для: парсеров на образцах, свёртки в проблему, срабатывания правил, сопоставления ответа с инцидентом.

## 18. Синтетические данные алертов

### 18.1. Почему данные генерируются

Реальные сообщения систем мониторинга заказчиком не предоставлены и в рамках работы предоставлены не будут: исторический массив содержит сведения о внутренней инфраструктуре и не выносится за периметр. Поэтому весь датасет — от единичных сообщений до потока за сутки — создаётся синтетически.

Это не компромисс, а осознанное проектное решение с двумя следствиями. Первое: генератор становится частью продукта, а не временным костылём — он нужен для регрессионного тестирования правил, для симулятора и для нагрузочных проверок. Второе: качество генератора напрямую определяет убедительность демонстрации, поэтому реалистичность формата важнее объёма.

**Главный критерий реалистичности:** сообщение должно быть неотличимо по форме от настоящего вывода соответствующей системы мониторинга. Инженер, работавший с Zabbix, при взгляде на демонстрацию не должен усомниться в происхождении текста.

### 18.2. Модель инфраструктуры

Основа генератора — описание вымышленной, но правдоподобной инфраструктуры пилотного периметра. Файл `datagen/inventory.yaml`.

Состав, соответствующий условиям кейса (Блок разведки и добычи, 4 филиала, Zabbix для АСУ ТП и SolarWinds для сетевого оборудования):

| Сущность | Количество | Атрибуты |
|---|---|---|
| Площадки (филиалы) | 4 | код, название, часовой пояс, дочернее общество |
| Подсети | 12–16 | CIDR, привязка к площадке, назначение |
| Сетевое оборудование | 30–40 | коммутаторы ядра и доступа, маршрутизаторы, каналы связи |
| Серверы и виртуальные машины | 60–80 | имя, FQDN, IP, инвентарный номер, ОС, версия пакетов |
| Контроллеры АСУ ТП | 20–30 | привязка к кусту или установке, геотег |
| Компоненты | 3–6 на объект | диски, интерфейсы, службы, процессы |
| Бизнес-сервисы | 10–15 | критичность, SLA, владельцы |
| Сотрудники | 87 | роль, филиал, зона ответственности, идентификатор TrueConf |
| Дочерние общества | 3–4 | у части объектов — два владельца одновременно |

Требования к модели:

1. **Топология связна.** У каждого сервера есть коммутатор доступа, у коммутатора доступа — коммутатор ядра, у площадки — канал связи и питание. Без этого нечего коррелировать.
2. **Имена конфликтуют намеренно.** На разных площадках существуют объекты с одинаковыми короткими именами (`app-01`, `db-02`), а компоненты `C:`, `eth0`, `nginx` повторяются на десятках объектов. Это проверяет раздел 4.1 — если корреляция ошибочно свяжет диски `C:` с разных хостов, генератор это выявит.
3. **Владение неоднородно.** У части объектов два дочерних общества, у части — ни одного (проверка карантина).
4. **Идентификаторы неполны.** У 15–20% объектов отсутствует FQDN или инвентарный номер, у части IP менялся — это нагрузка на резолвер.
5. **Версии ПО различаются.** Часть объектов обновлена вчера, часть месяц назад — это материал для оси корреляции «версия ПО».

### 18.3. Шаблоны сообщений источников

Файлы `datagen/templates/*.yaml`. Задача — воспроизвести формат конкретной системы, включая её особенности.

**Zabbix.** Ключевые свойства формата: сообщение собирается по настраиваемому шаблону действия; типичный вид включает статус (`PROBLEM` / `RESOLVED`), имя триггера, узел, время, уровень важности и значение элемента данных; уровни важности — `Not classified`, `Information`, `Warning`, `Average`, `High`, `Disaster`; при восстановлении приходит парное сообщение с тем же именем триггера.

```yaml
system: zabbix
severity_levels: [Not classified, Information, Warning, Average, High, Disaster]
templates:
  host_unreachable:
    firing: |
      PROBLEM: {trigger_name}
      Host: {host} ({ip})
      Trigger: {trigger_name}
      Severity: {severity}
      Time: {ts:%Y.%m.%d %H:%M:%S}
      Item value: ICMP ping = 0
    resolved: |
      RESOLVED: {trigger_name}
      Host: {host} ({ip})
      Duration: {duration}
  disk_space:
    firing: |
      PROBLEM: Free disk space is less than {threshold}% on volume {component}
      Host: {host}
      Severity: {severity}
      Item value: {value}%
```

**SolarWinds.** Ключевые свойства: раздельные действия trigger и reset; узел и интерфейс как отдельные сущности; текст ближе к телеграфному стилю сетевого мониторинга.

```yaml
system: solarwinds
severity_levels: [Informational, Warning, Critical, Serious]
templates:
  interface_down:
    firing: |
      Alert: Interface {component} on {node} is Down
      Node: {node} ({ip})
      Interface: {component}
      Status: Down
      Triggered: {ts:%m/%d/%Y %I:%M:%S %p}
    reset: |
      Reset: Interface {component} on {node} is Up
```

Требования к шаблонам:

1. **Разные форматы времени у разных источников** — один в 24-часовом формате с точками, другой в американском 12-часовом. Это проверяет нормализацию.
2. **Разные наборы уровней важности** — шесть у одного, четыре у другого, с разными названиями. Проверяет раздел 7.
3. **Разные способы указания объекта** — где-то короткое имя, где-то FQDN, где-то только IP. Проверяет резолвер.
4. **Часть сообщений намеренно «грязная»** — лишние переносы, пустые поля, обрезанные значения, кириллица вперемешку с латиницей в именах узлов. Реальные сообщения такими и бывают.
5. **Отсутствие сообщения о восстановлении у части классов** — проверяет цикл сверки и TTL из раздела 5.

### 18.4. Сценарии инцидентов

Файлы `datagen/scenarios/*.yaml`. Сценарий описывает не одиночное сообщение, а причинно-следственную цепочку с временными задержками.

```yaml
scenario: p1_switch_cascade
description: Отказ коммутатора доступа и каскад недоступности хостов
probability_per_day: 0.8
timeline:
  - at: +0s
    source: solarwinds
    template: node_down
    target: { role: access_switch, site: any }
    role_in_incident: root
  - at: +8s..+45s
    source: zabbix
    template: host_unreachable
    target: { relation: children_of_root, count: 8..16 }
    role_in_incident: symptom
  - at: +20s..+90s
    source: zabbix
    template: service_down
    target: { relation: services_on_children, count: 3..7 }
    role_in_incident: symptom
  - at: +12m..+40m
    source: solarwinds
    template: node_up
    target: { same_as: root }
    role_in_incident: resolution
expected:
  incidents: 1
  root_symptom_class: node_down
  suppressed_min: 10
```

Поле `expected` — не документация, а **эталон для автотестов**: генератор знает истинную структуру инцидента, поэтому качество корреляции измеряется объективно. Это даёт метрики точности и полноты для дашборда и для презентации — без реальных данных их иначе взять неоткуда.

**Обязательный набор сценариев:**

| Сценарий | Что проверяет |
|---|---|
| Отказ коммутатора доступа с каскадом | топологическую корреляцию, свёртку симптомов |
| Отказ питания площадки | корреляцию по площадке, неоднозначность первопричины (питание или канал) |
| Заполнение диска с нарастанием 80 → 85 → 90 → 95% | повторы, тип сообщения `REPEAT`, упреждающий дедлайн |
| Остановка буровой установки (P0) | мгновенную доставку без окна корреляции, эскалацию, геотег |
| Нестабильный интерфейс, 40 переключений за 10 минут | детектор flapping |
| Массовые алерты после обновления пакета | ось корреляции «версия ПО» |
| Алерты в окне плановых работ | подавление ожидаемого, маршрутизацию исполнителю работ |
| Дубль: один факт от Zabbix и SolarWinds одновременно | межсистемную дедупликацию |
| Одиночный алерт без связей | что система не связывает то, что связывать не следует |
| Алерт по объекту вне CMDB | карантин и резервную маршрутизацию |

Последние два сценария не менее важны, чем первые: система, которая связывает всё подряд, хуже системы, которая не связывает ничего.

### 18.5. Фоновый шум

Кейс задаёт ориентир: 5400 событий в сутки, 65% закрываются без реакции в первые две минуты. Генератор воспроизводит эту пропорцию.

| Категория | Доля | Характер |
|---|---|---|
| Шум: кратковременные срабатывания, самовосстанавливающиеся | ~65% | пара «срабатывание — восстановление» с интервалом менее 2 минут |
| Информационные и низкого приоритета | ~20% | не требуют реакции, но требуют учёта |
| Значимые единичные | ~12% | требуют реакции, связей не имеют |
| Инциденты со сценарием | ~3% | из раздела 18.4 |

Распределение во времени: неравномерное, с суточным профилем — всплеск утром при запуске смены, провал ночью, случайные пики. Равномерный поток нереалистичен и делает демонстрацию неубедительной.

### 18.6. Требования к генератору

1. **Воспроизводимость.** Фиксированное зерно случайности даёт идентичный набор. Демонстрация не должна зависеть от удачи.
2. **Два режима.** Пакетный — набор за период в файл; потоковый — отправка в шлюз в реальном или ускоренном времени (`--speed 60` для проигрывания суток за минуты).
3. **Формат вывода.** JSON Lines: одна строка — одно сообщение с метаданными (`source`, `sent_at`, `raw_body`, `scenario_id`, `ground_truth`). Поле `ground_truth` при подаче в платформу отбрасывается и используется только для оценки качества.
4. **Отправка в тех же протоколах, что и настоящие источники** — webhook и syslog, а не прямая запись в базу. Иначе не тестируется шлюз и парсер.
5. **Параметризация**: период, интенсивность, доля шума, перечень включённых сценариев, зерно.

```bash
python -m datagen.generate --days 1 --seed 42 --out out/day1.jsonl
python -m scripts.replay out/day1.jsonl --speed 60 --target http://gateway:8080
python -m scripts.replay --scenario p1_switch_cascade --live   # для демонстрации
```

### 18.7. Что генератор даёт помимо разработки

| Применение | Как используется |
|---|---|
| Симулятор правил (раздел 6.4) | прогон нового правила по сгенерированной истории |
| Метрики точности корреляции | сравнение результата с `ground_truth` — объективная оценка вместо декларации |
| Нагрузочная проверка | воспроизведение шторма 500 событий в минуту |
| Демонстрация экономического эффекта | подсчёт реального снижения шума на известном датасете |
| Регрессионное тестирование | фиксированный набор в `fixtures/` не меняется между сборками |

### 18.8. Оговорка для презентации

Синтетическое происхождение данных **проговаривается явно**, а не скрывается. Формулировка для защиты: инфраструктура и сообщения смоделированы по описанию из кейса, поскольку реальные данные не выносятся за периметр; при этом форматы сообщений воспроизводят фактический вывод Zabbix и SolarWinds, а структура инцидентов задана заранее, что позволяет измерить точность корреляции объективно — на реальных данных без разметки такая оценка была бы недоступна.

Попытка выдать синтетику за реальные данные — единственный способ потерять доверие эксперта мгновенно и необратимо. Честное объяснение, наоборот, демонстрирует понимание ограничений.

## 19. Сценарий демонстрации и критерии приёмки

### 19.1. Сценарий

Полный цикл в реальном времени, без вмешательства оператора:

1. Событие из Zabbix поступает в шлюз, проходит разбор, резолв, свёртку в проблему.
2. Подписанный инженер получает `NEW` в TrueConf. Неподписанный не получает ничего — показывается второй клиент.
3. Через 30 секунд приходят связанные события из SolarWinds. Коррелятор связывает их правилом, приходит `SUPPLEMENT` с первопричиной и счётчиком связанных.
4. Инженер отправляет `/граф INC-4471` — в чат приходит изображение графа инцидента.
5. Поступает третий алерт, не покрытый правилами. Инженер отвечает на уведомление `следствие` — бот предлагает кандидатов, затем правило с результатом симуляции. Инженер подтверждает.
6. Отправляется четвёртый алерт того же класса — он автоматически сворачивается новым правилом, отдельного сообщения нет.
7. В кабинете меняется подписка. Следующее событие приходит уже другому сотруднику.
8. Источник присылает восстановление — приходит `CLOSURE` с длительностью и MTTR.
9. Показывается дашборд с изменившимися метриками и журнал уведомлений с историей.

### 19.2. Соответствие критериям оценки

| Критерий кейса | Чем закрывается |
|---|---|
| Полный функционал: конфигурируемое подключение, настраиваемая маршрутизация, интеграция с TrueConf, дашборд, реальное время | шаги 1–9 |
| Последовательная и интерактивная демонстрация, изменение подписок на лету | шаг 7 |
| Комплексный ИИ-агрегатор: нормализация, дедупликация, корреляция, первопричина, маршрутизация, саммаризация | шаги 1, 3, 4, 5, раздел 13 |
| Подключение новых источников без изменения ядра | декларативные парсеры, раздел 5 стадия 1 |
| Импортозамещение | разделы 1.4 и 15.1 |
| LDAP/AD и автоотключение подписок при увольнении | раздел 14.1–14.2 |
| Экономический расчёт | раздел 16 |

## 20. Подводные камни

Перечень проверяется до начала разработки соответствующего модуля.

1. **Признак ответа во входящем сообщении.** Механика раздела 9.4 предполагает, что входящее сообщение содержит идентификатор сообщения, на которое отвечают. Это необходимо проверить на реальном сервере в первую очередь. Если признак недоступен — переходим на явное указание номера инцидента в тексте (`взял INC-4471`) и на ссылки в кабинет; функциональность сохраняется, удобство снижается. Реализовать обе формы сразу.
2. **Версия TrueConf Server.** Часть методов требует 5.5.2+ или 5.5.3+. Версию развёрнутого сервера выяснить до планирования функций.
3. **Неидемпотентность создания каналов.** Повторный вызов создаст дубликат. Идентификаторы каналов хранить в базе, создание — только явной административной операцией.
4. **Лимит 4096 символов.** Сводки и списки связанных обязаны использовать безопасное разбиение; тест на длинной сводке обязателен.
5. **Ограничения на файлы задаёт администратор сервера.** Перед отправкой графа проверять доступный размер и разрешённые расширения; предусмотреть упрощённый граф.
6. **Обрыв WebSocket.** Без исходящей очереди уведомления будут теряться при переподключении. Очередь реализуется до первой отправки, а не после.
7. **Эхо-петли при нескольких экземплярах бота.** Пропуск собственных сообщений включён по умолчанию, но при запуске нескольких экземпляров нужен единый владелец отправки — иначе дубликаты.
8. **Расхождение часов источников.** Без двух временных меток порядок событий в корреляции будет случайным.
9. **Дрейф шаблонов источника.** Без детектора парсер тихо деградирует, и алерты перестают маршрутизироваться, оставаясь формально «обработанными».
10. **Ошибка корреляции.** Без сторожевого таймера свёрнутый симптом может скрыть самостоятельный инцидент. Таймер реализуется одновременно со свёрткой, а не позже.
11. **Привязка учётной записи.** Идентификатор пользователя мессенджера не равен учётной записи каталога. Без подтверждённой привязки любые действия через бота небезопасны.
12. **Слишком крупный граф.** Более 40 узлов нечитаемы на экране телефона. Агрегация узлов обязательна, а не желательна.
13. **Синтетика, подогнанная под решение.** Главный риск раздела 18: сгенерировать данные, на которых корреляция работает идеально, потому что генератор и коррелятор писал один человек с одними допущениями. Противоядие: сценарии с неоднозначной первопричиной, конфликтующие имена объектов, объекты вне CMDB и одиночные несвязанные алерты закладываются в набор обязательно, а не по остаточному принципу. Если точность корреляции на синтетике равна 100%, плох набор, а не хорош коррелятор.
```
