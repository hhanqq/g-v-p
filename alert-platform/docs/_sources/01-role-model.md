# Платформа «Диспетчер». Ролевая модель

**Статус документа:** проект целевой ролевой модели с фиксацией фактической реализации на 10.08.2026  
**Назначение:** основание для настройки LDAP/AD, проверок авторизации в Go Admin API, прав в личном кабинете и TrueConf, аудита доступа и приёмочных испытаний.

## 1. Правила чтения документа

В платформе одновременно существуют продуктовые роли людей, группы ответственности за оборудование и технические учётные записи процессов. Смешение этих трёх сущностей опасно: членство сотрудника в дежурной группе не должно давать ему административные права, а учётная запись `delivery-planner` не должна считаться «администратором» только потому, что ей технически доступна вся база данных.

Каждое существенное утверждение помечено одним из статусов:

- **ФАКТ** — подтверждено текущим кодом, схемой БД или конфигурацией репозитория;
- **ЦЕЛЕВОЕ** — требование спецификации или предлагаемая модель для промышленной эксплуатации;
- **РАЗРЫВ** — целевая возможность отсутствует, реализована частично либо фактические права шире требуемых.

Эта маркировка принципиальна: таблицы ниже не выдают желаемые права за уже работающий RBAC. Источниками фактов служат `ALERT-PLATFORM-SPEC.md` (разделы 4.2, 8, 11, 14), `SECURITY.md`, `ARCHITECTURE.md`, миграции `0000_baseline.sql` и `0007_groups.sql`, Go Admin API, React-маршруты и тестовый каталог `ldap/glauth.cfg`.

## 2. Принципы ролевой модели

1. **Минимально необходимые полномочия.** Сотрудник получает только данные своих сервисов и действия, необходимые для реакции; администратор — только свой класс настройки; аудитор — только чтение и выгрузку.
2. **Запрет наследования бизнес-ответственности в системные права.** «Дежурный по оборудованию» — адресат и исполнитель, а не администратор справочника оборудования.
3. **RBAC + ABAC.** Роль определяет допустимую операцию, а атрибуты ограничивают набор объектов: площадка (`site`), дочернее общество (`subsidiary`), сервис (`service_id`), объект/тип оборудования и смена.
4. **Разделение обязанностей (SoD).** Автор критичного правила не утверждает собственное изменение; администратор не подменяет аудитора; сервисная учётная запись не используется человеком.
5. **Deny by default.** Новый endpoint, ресурс или операция закрыты до явного включения в policy.
6. **Проверка на сервере.** Скрытие пункта меню не является авторизацией. Решение принимается Admin API или соответствующим runtime-компонентом для каждого запроса.
7. **Прослеживаемость.** Выдача роли, изменение области, административная мутация, подтверждение инцидента и экспорт оставляют запись с субъектом, временем, результатом и объектом.

## 3. Субъекты доступа

### 3.1. Продуктовые роли людей

| Роль | Назначение и типичная область | Фактическое состояние | Целевые ограничения |
|---|---|---|---|
| **Сотрудник** | Пользователь оповещений. Управляет собственными подписками, просматривает относящиеся к нему активные алерты и архив. Область — собственная учётная запись и вычисленный набор сервисов/филиалов. | **ФАКТ:** успешно аутентифицированный LDAP-пользователь, не входящий в `admins`, попадает в общую React-консоль как `is_admin=false`; демонстрационные сотрудники заведены в каталожной группе `employees`, но код входа отдельно её не проверяет. Token-based кабинет позволяет создавать и удалять собственные подписки и смотреть текущие алерты. | **ЦЕЛЕВОЕ:** общий каталог сотрудников, инциденты и история фильтруются по области пользователя; персональные данные коллег недоступны без специальной роли. |
| **Дежурный** | Операционный исполнитель текущей смены: получает уведомления, подтверждает реакцию, видит инциденты и оборудование своей зоны, при необходимости инициирует эскалацию. Область вычисляется из расписания, группы и оборудования. | **ФАКТ:** ответ на доставленное TrueConf-сообщение записывает `acknowledged_at/by`; таблицы `groups`, `group_members`, `group_equipment_scope` описывают группы и зоны оборудования. **РАЗРЫВ:** отдельной LDAP/сессионной роли дежурного и проверки этой зоны при чтении API нет. | **ЦЕЛЕВОЕ:** `duty_operator` с временным назначением по смене; ACK только для полученного инцидента или инцидента в его зоне; без прав менять маршрутизацию и справочники. |
| **Руководитель / владелец сервиса** | Контролирует сервис, получателей, SLA, эскалации и отчётность своей организационной области; проводит ре-аттестацию. Владелец сервиса является специализированным вариантом роли руководителя. | **ФАКТ:** спецификация предусматривает владельца сервиса, руководителя смены и эскалацию; `cmdb_ownership`, `cmdb_services`, `subscriptions`, `sla_rules` содержат часть атрибутов. **РАЗРЫВ:** роли руководителя/владельца, процесс подтверждения состава и endpoint ре-аттестации отсутствуют. | **ЦЕЛЕВОЕ:** `service_owner`/`manager`; права ограничены собственными сервисами и дочерними обществами; допускается утверждение адресатов и просмотр агрегированной аналитики, но не управление источниками или системными секретами. |
| **Администратор платформы** | Управляет эксплуатационными настройками платформы и справочниками в пределах делегированного административного профиля. | **ФАКТ:** членство в LDAP-группе `admins` попадает в подписанную сессию как `is_admin=true`. Только `admins` могут управлять источниками, создавать/редактировать сотрудников и оборудование, читать `audit_log`. | **РАЗРЫВ:** одна группа объединяет администраторов источников, маршрутизации и каталога; часть критичных write-endpoint доступна любому вошедшему сотруднику. **ЦЕЛЕВОЕ:** раздельные административные роли. |
| **Аудитор** | Независимо читает журнал действий, версии правил, отчёты о доступе и может выгружать доказательства; не меняет бизнес-данные. Область обычно общеплатформенная или ограниченная юрлицом. | **ФАКТ:** отдельной роли нет; `/api/audit` требует `admins`. | **РАЗРЫВ:** аудитор вынужден иметь избыточную административную роль, нарушая SoD. **ЦЕЛЕВОЕ:** `auditor` — read/export-only, без create/update/delete/activate. |

Спецификация дополнительно разделяет **администратора маршрутизации** и **администратора источников**. В целевой модели они должны быть профилями роли администратора, а не одним флагом:

- `routing_admin` — подписки, группы ответственности, дежурства, эскалации, SLA и сценарии;
- `source_admin` — паспорта источников, парсеры, токены интеграций, карантин и алиасы;
- `directory_admin` — сотрудники, оборудование, сервисы, владение и организационные атрибуты;
- `platform_admin` — эксплуатационная конфигурация и назначение перечисленных ролей, но не повседневное подтверждение инцидентов от имени дежурного.

### 3.2. Группы ответственности — не роли безопасности

**ФАКТ:** миграция `0007_groups.sql` вводит `groups`, членство подписчиков и область оборудования по `object_id`, `equipment_type` или `site`. API позволяет создавать группы, менять состав и область. Эти записи пригодны для маршрутизации и вычисления ответственности.

**РАЗРЫВ:** текущий Admin API не использует `group_equipment_scope` как фильтр авторизации при чтении инцидентов, оборудования или сотрудников. Поэтому наличие строки «группа обслуживает площадку X» сейчас нельзя трактовать как действующий ABAC. Также имя группы свободное и не связано с LDAP DN.

**ЦЕЛЕВОЕ:** группа ответственности отвечает на вопрос «кому направить и за что он дежурит», LDAP/AD-группа — «какую операцию разрешить», атрибутная policy — «над какими объектами». Связь между ними должна быть явной и аудируемой, например `directory_group_dn -> application_role + scope_source`, без принятия решения по совпадению текстовых имён.

| `changelog-worker` | Relay истории в Redpanda/ClickHouse и архив Signal в MinIO. | Общий DB principal `alert`, ClickHouse user `alert`, MinIO root credentials по умолчанию. | PostgreSQL read/claim только `change_events` и Signal tail; ClickHouse insert; отдельный S3 ключ только своего bucket/prefix. |
| `migrate`, `clickhouse-migrate`, `kb-index`, `demo-runner` | Миграции, индексирование базы знаний и синтетическое демо. | Используют привилегированные общие credentials соответствующих хранилищ. | Запускаемые отдельно batch-роли; `migrate` допускает DDL только в контролируемом окне, demo не присутствует в production. |

**РАЗРЫВ:** принципал `alert` с одинаковым паролем используется критическими и некритическими процессами. Компрометация одного контейнера даёт права, которые невозможно ограничить по таблицам, а журнал БД не различает процесс-инициатор. Требуются отдельные PostgreSQL роли, network policies и секреты; root-доступ MinIO не должен быть рабочей учётной записью приложения.

## 5. Фактическая матрица и разрывы авторизации

### 5.1. Что реализовано

- **ФАКТ:** вход выполняется двумя LDAP bind: `svc-search` ищет DN и `memberOf`, затем пароль проверяется bind под найденным DN. Пароль пользователя в БД платформы не хранится.
- **ФАКТ:** сессионная cookie подписана HMAC-SHA256, `HttpOnly`, `SameSite=Lax`, живёт 14 суток; `Secure` зависит от конфигурации. Сравнение подписи constant-time. Login limiter — пять неудач за пять минут на имя пользователя в памяти одного процесса.
- **ФАКТ:** только LDAP-группа `admins` превращается в `is_admin=true`; остальные успешно вошедшие пользователи имеют одинаковый `is_admin=false`. Группа `employees` сама по себе в коде не проверяется: доступ получает любой пользователь, которого поиск нашёл в LDAP и чей пароль прошёл bind.
- **ФАКТ:** `requireAdmin` применяется к источникам, `audit_log`, созданию/изменению сотрудников и оборудования. Источник при регистрации получает `X-Source-Token`.
- **ФАКТ:** все read-endpoint основной консоли за исключением публичной compliance-метрики требуют валидную сессию. Это списки инцидентов, алертов, сотрудников, оборудования, групп, сценариев, SLA, аналитика, integration status и change history.
- **ФАКТ:** персональный кабинет не использует LDAP-cookie. Доступ проверяется парой `trueconf_username + access_token`; token сравнивается constant-time. Создание/удаление подписки ограничено `subscriber_id`, извлечённым по этой паре.
- **ФАКТ:** ACK выполняется ответом на TrueConf-сообщение и связывается с `message_id`; Admin API отдельной ACK-ручки не имеет.
- **ФАКТ:** публичны `/api/compliance-metrics`, SPA-оболочка и demo routes; полная метрика `/api/metrics` требует сессии. React отдельно пропускает `/compliance` без входа.

### 5.2. Избыточные фактические права

| Разрыв | Доказуемое поведение | Риск / требуемое исправление |
|---|---|---|
| Любой вошедший пользователь видит общие данные | `withAuth` проверяет только наличие сессии; list/get incidents, alerts, employees, equipment, groups, scenarios, SLA, analytics и change history не применяют scope. | Утечка персональных и производственных данных между площадками/ДО. Добавить централизованный policy enforcement и row filters. |
| Write групп не admin-only | `createGroup`, `updateGroup`, `deleteGroup`, add/remove member и equipment scope не вызывают `requireAdmin`. | Сотрудник может изменить маршрутизацию/ответственность. Закрыть за `routing_admin`; покрыть негативными тестами. |
| Write сценариев и SLA не admin-only | create/update/activate/deactivate scenario и create SLA вызываются через `withAuth`, но не `requireAdmin`. | Изменение тракта уведомлений и SLA обычным сотрудником. Ввести maker-checker и специализированную роль. |
| Доступность сотрудника меняет любой вошедший | `setEmployeeAvailability` не проверяет admin, self или управление группой. | Исключение адресата/ошибочная маршрутизация. Разрешить self-service для себя и manager для подчинённой области; разделить типы статусов. |
| Admin/read distinction в UI неполна | `App.tsx` регистрирует одинаковые маршруты для всех вошедших; `Sidebar.tsx` не фильтрует меню по `is_admin`. Источники и аудит существуют как routes, но не включены в основной NAV. | UI не объясняет права и может предлагать запрещённые действия; серверные проверки сохраняются, но UX и тестируемость хуже. Рендерить меню по capabilities, не заменяя серверную защиту. |
| Нет auditor role | `/api/audit` требует флаг admin. | Независимый аудитор получает write-права администратора. Добавить read-only роль и отдельный export endpoint. |
| Нет export-контракта | В спецификации журнал уведомлений предусматривает выгрузку, но в исследованных Admin API/React маршрутах отдельной операции экспорта нет. | Невозможно формально выдать и ограничить право «экспорт». Реализовать асинхронную выгрузку с фильтром области и аудитом. |
| Нет подтверждённого LDAP↔TrueConf mapping | TrueConf handler автоматически создаёт `Subscriber` для любого автора команды `/кабинет` или `/алерты` и выдаёт token. LDAP-подтверждение связки, требуемое разделом 14.1 спецификации, не выполняется. | Владелец TrueConf-логина получает кабинет, даже если логин не подтверждён каталогом; deprovision исправляет это лишь позднее и не заменяет первичную привязку. Нужен одноразовый flow подтверждения через LDAP-сессию. |
| Долгая автономная LDAP-сессия | Роль `is_admin` вложена в подписанную cookie на 14 дней; каждый запрос LDAP не проверяет. Удаление из `admins` не отзывает уже выданную cookie. | Остаточный привилегированный доступ до expiry. Уменьшить TTL, хранить server-side session/version, проверять статус/роль периодически и поддержать принудительный отзыв. |

### 5.3. Недостающие целевые возможности

В текущей схеме нет таблиц назначений application roles, grants со сроком действия, владельцев ролей, заявок/согласований и результатов ре-аттестации. `subscribers.active` — статус получателя, а не универсальный статус доступа. `cmdb_ownership` связывает объект/сервис/дочернее общество, но не назначает человеку роль владельца. `groups` не хранит тип группы, владельца, срок членства и источник назначения. Нет явных permissions для просмотра, подтверждения, экспорта и управления отдельными типами ресурсов.

Поэтому **РАЗРЫВ:** роль руководителя, дежурного, владельца сервиса, аудитора и специализированных администраторов пока нельзя надёжно выразить или проверить. Добавление только новых пунктов в GLAUTH недостаточно — требуется модель policy и серверная проверка на каждой операции.

## 6. Область действия (ABAC)

Целевая область вычисляется как пересечение, а не объединение всех возможных осей:

```text
effective_scope(subject, action) =
    role_permissions(action)
    ∩ directory_scope(site, subsidiary, org_unit)
    ∩ responsibility_scope(service, object, equipment_type)
    ∩ temporal_scope(shift, valid_from, valid_until)
```

Для сотрудника дополнительно действует `subject_id = resource.owner_id` на self-service. Для дежурного временная смена сужает статическую группу. Для владельца сервиса область выводится из формального назначения владения, а не из подписки: подписка говорит, что пользователь хочет получать, но не доказывает право управлять сервисом. Для аудитора scope применяется к просматриваемым данным, но не разрешает мутации.

**ФАКТ:** в БД уже есть пригодные строительные блоки: `site`, `subsidiary`, `service_id`, `object_id`, `equipment_type`, `group_members`, `employee_availability`, временные поля доступности и связь объектов с сервисами. **РАЗРЫВ:** они используются маршрутизацией и интерфейсом, но не собраны в единое авторизационное решение.

Рекомендуемый серверный контракт: endpoint декларирует `resource`, `action` и способ загрузки scope; middleware получает актуальные grants субъекта, а SQL-запрос обязан принимать вычисленный scope. Проверка после выборки недостаточна: она может раскрыть количество записей и ухудшает производительность. Для мутаций проверка и изменение выполняются в одной транзакции, с блокировкой изменяемой строки.

## 7. Разделение обязанностей (SoD)

| Конфликт | Целевое правило |
|---|---|
| Администратор ↔ аудитор | Аудитор не имеет write-разрешений; platform admin не может удалять/править аудит. Выгрузки администратора также журналируются и доступны аудитору. |
| Автор сценария/правила ↔ утверждающий | Production-активацию выполняет другой субъект с правом approver. Экстренный bypass требует причины, ограниченного срока и последующего review. |
| Владелец сервиса ↔ routing admin | Владелец подтверждает бизнес-состав и SLA; routing admin технически применяет policy, но не утверждает собственное изменение состава. |
| Администратор каталога ↔ назначение собственной роли | Нельзя самостоятельно выдать себе `platform_admin`, `auditor` или расширить scope; требуется второй уполномоченный. |
| Дежурный ↔ изменение истории | Дежурный подтверждает реакцию, но не редактирует исходный Signal, время доставки или чужой ACK. Ошибка исправляется компенсирующей записью. |
| Runtime account ↔ интерактивный пользователь | Сервисные credentials запрещены для входа людей; у процессов нет LDAP/SPA-сессий. |

**ФАКТ:** сценарии версионируются при изменении графа, автор и время частично сохраняются; Signal задуман как WORM, а административные действия пишут `audit_log`/`change_events`. **РАЗРЫВ:** четырёхглазого утверждения нет, `audit_log` не защищён отдельной DB-ролью от UPDATE/DELETE, а многие записи change history выполняются best-effort вне общей транзакции. Это полезная наблюдаемость, но не достаточное доказательство неизменяемого аудита.

## 8. Жизненный цикл доступа

### 8.1. Целевой процесс

1. **Найм/перевод:** личность и оргатрибуты приходят из AD/HR; platform account вручную не создаётся как независимый источник истины.
2. **Заявка:** запрашиваются роль, scope, основание, владелец доступа и срок. Привилегированная роль всегда срочная либо периодически подтверждаемая.
3. **Согласование:** руководитель подтверждает бизнес-потребность; владелец роли/ИБ — конфликт SoD; система не позволяет самоутверждение.
4. **Предоставление:** AD-группа или IGA grant синхронизируется в policy store. TrueConf identity связывается с directory identity и подтверждается через LDAP-сессию.
5. **Использование:** роль и scope проверяются на каждом запросе; временная дежурная роль автоматически начинается и заканчивается по расписанию.
6. **Ре-аттестация:** ежеквартально владельцы сервисов подтверждают получателей, руководители — роли, platform owner — сервисные учётки. Неподтверждённое назначение истекает.
7. **Перевод/отпуск/делегирование:** старый scope отзывается до выдачи нового; делегирование имеет срок и не передаёт административные полномочия автоматически.
8. **Увольнение:** directory disable отзывает сессии, application grants, TrueConf token и участие в активной маршрутизации. Если пользователь был единственным адресатом, закрытие процедуры блокируется до назначения преемника.
9. **Удаление:** после retention персональные данные минимизируются, но идентификатор автора в аудите сохраняется в допустимой форме.

### 8.2. Что делает система сейчас

**ФАКТ:** `deprovision-worker` примерно периодически получает список LDAP пользователей. Если каталог недоступен или вернул подозрительно пустой список, никого не деактивирует. Если активного `Subscriber` нет в каталоге, ставит `active=false` и пишет действие `deprovision`. Это fail-safe относительно массового ошибочного отзыва. Записи `subscriptions` физически не удаляются; неактивный подписчик исключается из активной доставки.

**РАЗРЫВ:** процесс не отзывает 14-дневную Admin API cookie, не ротирует/аннулирует `access_token`, не проверяет «последнего адресата сервиса», не создаёт блокирующую задачу преемника и не реализует квартальную ре-аттестацию. Ручная установка `active=true` доступна администратору через update сотрудника, но formal approval не зафиксирован.

## 9. LDAP/AD mapping

### 9.1. Фактическое отображение

| Directory artefact | Application representation |
|---|---|
| Пользователь LDAP `uid` | `sessionPayload.Username`; независимо — `subscribers.trueconf_username` при совпадающем имени |
| `ou=admins,ou=groups,<baseDN>` | `is_admin=true`, actor role `admin` в части `change_events` |
| Любой другой найденный LDAP пользователь | `is_admin=false`, actor role `user` |
| GLAUTH `employees` | Существует в каталоге, но прямой проверки членства для входа в Go `Authenticate` нет |
| Application `groups` | Отдельные строки PostgreSQL; автоматической связи с LDAP group DN нет |
| TrueConf author id | Часть до `@`; по ней находится/автоматически создаётся `Subscriber` и выдаётся access token |

Тестовый каталог содержит `admin1`, обычных пользователей `engineer1`, `tester`, `tester2`, `noc1` и service account `svc-search`. Это демонстрационный GLAUTH, а не доказательство наличия промышленной AD-интеграции конкретного заказчика.

### 9.2. Целевое отображение

Не следует кодировать роли сравнением коротких имён групп. Нужен конфигурируемый mapping по полному immutable group/object identifier:

| Пример directory-группы | Application role | Источник scope |
|---|---|---|
| `GG-DISPATCHER-USERS` | `employee` | атрибуты пользователя/сервисы |
| `GG-DISPATCHER-DUTY-<SITE>` | `duty_operator` | `<SITE>` + расписание дежурства |
| `GG-DISPATCHER-SERVICE-OWNERS-<SERVICE>` | `service_owner` | `<SERVICE>` и связанные ДО |
| `GG-DISPATCHER-ROUTING-ADMINS` | `routing_admin` | делегированные сервисы/площадки |
| `GG-DISPATCHER-SOURCE-ADMINS` | `source_admin` | перечень source instances/sites |
| `GG-DISPATCHER-AUDITORS` | `auditor` | утверждённая область проверки |
| `GG-DISPATCHER-PLATFORM-ADMINS` | `platform_admin` | платформа, без автоматического бизнес-scope |

Mapping версионируется, изменение требует аудита. В сессии лучше хранить короткий идентификатор server-side session, а актуальные роли/grants получать из кэша с малым TTL и revocation version. При недоступном LDAP уже созданная непривилегированная сессия может кратко продолжить работу по принятой политике, но повышение роли запрещается; для критичных admin-действий допустима step-up проверка.

## 10. Аудит ролевой модели

Должны регистрироваться: успешный и неуспешный вход; блокировка limiter; выдача, изменение, истечение и отзыв роли/scope; подтверждение LDAP↔TrueConf; выпуск, просмотр и ротация source token; создание/изменение/активация сценария или SLA; состав группы; подписка/отписка; ACK; экспорт; отказ авторизации; действие сервисной учётной записи.

Минимальная запись: UTC timestamp, correlation/request ID, actor type (`human/service`), immutable actor ID, effective roles, action, resource type/id, scope decision, before/after для мутаций, result, reason, source IP/client и approver/change ticket при SoD. Секреты, пароли, session cookie, access token и полные source token в журнал не помещаются.

**ФАКТ:** `audit_log` хранит `actor`, `action`, `target`, `detail`, `created_at`; `change_events` добавляет actor role, resource, before/after и result. Источники, группы, сотрудники, оборудование, подписки и часть сценариев пишут аудит. Login failure также журналируется. **РАЗРЫВ:** нет полного журнала allow/deny решений, назначения ролей, экспорта и просмотра секретов; actor role различает только `admin/user/system`; неизменяемость на уровне БД и WORM-retention для audit не показаны. Аудит следует писать атомарно с доменной мутацией в transactional outbox, а затем переносить в защищённое хранилище с контролем целостности.

## 11. Приоритетный план устранения разрывов

1. **P0 — закрыть privilege escalation:** добавить admin/specialized-role check на все write endpoints групп, сценариев, SLA и доступности; создать негативные тесты для `is_admin=false`.
2. **P0 — ввести scope на чтение:** не выдавать обычному сотруднику весь каталог сотрудников, все инциденты и change history. Начать с персональных данных и межфилиального разделения.
3. **P0 — подтвердить TrueConf identity:** выдавать кабинетный token только после связи с существующим directory subject; обеспечить отзыв/ротацию token при увольнении и компрометации.
4. **P1 — разложить `admins`:** `source_admin`, `routing_admin`, `directory_admin`, `platform_admin`, отдельно `auditor`; мигрировать endpoint policy с coarse boolean на capability set.
5. **P1 — server-side lifecycle:** короткие сессии, принудительный отзыв, актуальная проверка роли, срочные grants и quarterly access review.
6. **P1 — maker-checker:** draft/approve/apply для production-сценариев, SLA, маршрутизации и source changes; автор не утверждает собственное изменение.
7. **P1 — изолировать runtime identities:** отдельные DB principals и секреты, запрет login, минимальные GRANT, различимые actor IDs; убрать root/default credentials из runtime.
8. **P2 — формализовать export и аудит:** асинхронные выгрузки с scope, watermark/подписью и audit event; tamper-evident retention для security audit.
9. **P2 — ре-аттестация и молчаливые зоны:** owner assignment, quarterly attestation, проверка последнего адресата и блокирующий workflow преемника.

## 12. Критерии приёмки

- Обычный сотрудник получает `403` на каждый административный write endpoint и не видит данные вне своего scope.
- Дежурный может ACK только доставленный ему инцидент или инцидент активной зоны; окончание смены прекращает право без ручного вмешательства.
- Руководитель подтверждает состав своих сервисов, но не меняет source token и не читает чужие персональные данные.
- Аудитор видит и экспортирует аудит, но любой его POST/PUT/DELETE к доменным ресурсам возвращает `403`.
- Автор сценария не может активировать свою версию; approval и apply имеют разных actor IDs.
- Удаление пользователя из привилегированной AD-группы отзывает доступ в пределах установленного SLA, включая ранее выданную сессию.
- Удаление пользователя из каталога деактивирует доставку и кабинетный token; единственный адресат сервиса вызывает блокирующее предупреждение.
- Компрометация credentials одного runtime-компонента не даёт чтения/записи несвязанных таблиц.
- Каждое изменение grant, отказ авторизации, ACK и экспорт обнаруживаются по correlation ID; в журнале нет секретов.
- Повторное применение одной операции остаётся идемпотентным, а конкурентные runtime workers используют существующий безопасный queue/outbox pattern.

## 13. Вывод

Текущая система имеет рабочую базовую аутентификацию LDAP, две фактические сессионные категории (`admin` и `user`), персональный TrueConf token, admin-only защиту части чувствительных endpoint и аудит ряда мутаций. Это достаточная основа для развития, но ещё не полная ролевая модель из спецификации.

Главные несоответствия — отсутствие специализированных ролей и ABAC, чрезмерное чтение для любого вошедшего, незащищённые write-endpoint групп/сценариев/SLA/доступности, отсутствие отдельного аудитора, неподтверждённая LDAP↔TrueConf связка и общий DB principal runtime-процессов. До их закрытия роли «дежурный», «руководитель», «владелец сервиса» и «аудитор» следует обозначать как целевые, а не как реализованные permissions.

### 13.1. Решение для передачи в реализацию

| Контрольная точка | Решение | Доказательство завершения |
|---|---|---|
| Базовая граница доступа | Сначала закрыть P0 write/read разрывы, затем расширять UI | Негативные API-тесты и scope-тесты проходят для каждой роли |
| Источник ролей | Утвердить immutable AD group mapping и модель срочного отзыва | Версионированный mapping, журнал изменения и проверенный revoke SLA |
| Разделение полномочий | Ввести специализированные capabilities и maker-checker | Автор не может применить собственную production-конфигурацию |
| Допуск в production | Разрешить только после проверки TrueConf identity, DB grants и audit retention | Подписанные протоколы IAM, БД и ИБ; непроверенных пунктов не осталось |
