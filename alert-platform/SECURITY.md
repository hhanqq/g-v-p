# Диспетчер — безопасность: угрозы и меры

Критерий кейса «Информационная безопасность» — перечень актуальных угроз
и соответствующих технических мер. Все меры ниже реализованы и проверены
вживую (не только описаны), кроме явно помеченных как принятый риск.

## 1. Модель угроз

| Угроза | Вектор | Мера |
|---|---|---|
| Несанкционированный доступ к админ-функциям | Прямой запрос к SPA/API источников и аудита без сессии | LDAP/AD bind + подписанная HttpOnly session-cookie + проверка группы `admins` — раздел 6 ниже |
| Компрометация чужих подписок | Угадывание чужого TrueConf-логина в URL личного кабинета | Access-токен, выдаваемый только ботом в ответ на сообщение ОТ этого логина в TrueConf (личность подтверждает сам канал, не URL) — `services/delivery_trueconf/handlers.py` и Go `adminapi/personal.go` |
| Утечка пароля пользователя | Хранение пароля в БД платформы | Платформа пароль вообще не хранит и не видит — только LDAP/AD знает и проверяет пароль (`ldap_auth.authenticate`, bind под точным DN пользователя) |
| Компрометация API интеграции источников | Подмена/спам через `POST /api/v1/ingest/raw` | Идемпотентность по `(source_instance, hash)`, WORM-запись (раздел И3). Плюс токен-аутентификация: каждый источник, зарегистрированный через раздел «Источники», получает `api_token`, обязательный заголовком `X-Source-Token` (`go-platform/internal/gateway/http.go`, `subtle.ConstantTimeCompare`); все источники пилота (все 9 зарегистрированных инстансов на демо-стенде, 2026-08-09) защищены. **Остаточный, осознанный риск**: полный mTLS/allow-list по IP не реализован — следующий шаг для продакшн-периметра за пределами пилота. |
| Подбор пароля (brute-force) | Многократные попытки входа в `/api/auth/login` | Rate limiter на логин — не более 5 неудачных попыток за 5 минут на один логин, сброс при успешном входе (`go-platform/internal/adminapi/auth.go`) |
| Продолжение доступа уволенного сотрудника | Подписки остаются активными после увольнения | Автоотключение подписок при сверке с LDAP-каталогом (`packages/common/deprovision.py`), ~30с цикл, живьём проверено (см. память проекта — «уволенный» `noc1` корректно деактивирован) |
| Утечка данных во внешние облака | Передача содержимого алертов сторонним AI-API | ИИ-модуль — локальный self-hosted Ollama (`packages/ai/`), обращений к внешним облачным LLM нет нигде в коде |
| Timing-атака на сравнение токенов | Побайтовое сравнение `access_token` | `subtle.ConstantTimeCompare()` в Go token-based handlers |
| Отказ ИИ-компонента как вектор отказа в обслуживании | Недоступность/таймаут Ollama блокирует основной поток | Раздел И5 применён во всех 7 ИИ-сценариях: сбой ИИ никогда не блокирует и не роняет доставку/конвейер, только убирает необязательное дополнение — **проверено живым отказом** 2026-08-10: `systemctl stop ollama`, событие всё равно принято (`202`, 0с), разобрано, проблема создана, уведомление доставлено (`status=sent`, пустой `ai_summary`) |
| Бесследное изменение/удаление истории алертов | Прямой доступ к БД или баг приложения | `Signal` — WORM-таблица (раздел И3), приложение никогда не выполняет UPDATE/DELETE над ней |
| Несанкционированный доступ к Redpanda/ClickHouse/MinIO (раздел «История изменений») | Прямое подключение к брокеру/БД/S3 из интернета | Все три биндятся на `127.0.0.1` (docker-compose), проверено внешним сканом портов с публичного IP — `Connection refused` на всех пяти хостовых портах. **Остаточный, осознанный риск**: у Redpanda вообще нет аутентификации (полагается только на сетевую изоляцию), у ClickHouse/MinIO — дефолтные учётные данные того же типа, что раньше были у Postgres; приемлемо, пока периметр закрыт снаружи, кандидат на реальные секреты/TLS при расширении за пределы пилота. |
| Несанкционированное подключение к primary по протоколу репликации (раздел «Инфраструктура» — резервирование) | Роль `replicator` с правом REPLICATION | `pg_hba.conf` разрешает `replication`-подключения этой роли только из подсети docker-compose (`172.18.0.0/16`, `scram-sha-256`) — не с любого хоста и не с публичного IP; сам порт Postgres биндится на `127.0.0.1` (раздел 1 выше). Пароль сгенерирован (`openssl rand -hex`, не дефолтный demo-пароль остального стенда), т.к. эта роль даёт доступ на чтение ВСЕЙ БД через `pg_basebackup`, не только к одной таблице. |
| Вытеснение платформенной ИИ-модели с единственной GPU посторонней нагрузкой | `open-webui` (не часть проекта, `network_mode: host`) слушал `0.0.0.0:3000` — публично достижим, `OLLAMA_KEEP_ALIVE=-1` означает: чужой запрос выгружает нашу модель, чтобы освободить VRAM | Найдено при разборе критерия «Инфраструктура» (2026-08-10): T4 15 ГБ VRAM, наша модель `log-reader` в одиночку занимает 13,9 ГБ (90%) — свободного места на конкурентную модель физически нет. Порт 3000 закрыт снаружи тем же iptables-паттерном, что раньше применён к Ollama (`ACCEPT` с `127.0.0.1`, затем `DROP`, персистентно) — проверено внешним сканом (`Connection refused`) и внутренним доступом (200 с loopback). Сервис и модели не удалены, только недоступны снаружи. |

## 2. Авторизация пользователей

- **Администраторы платформы** (`/app`, `/api/sources`, `/api/audit`) — LDAP/AD (см. раздел 6), группа `admins` для изменяющих и audit-функций.
- **Подписчики** (личный кабинет `/me/`) — токен, выдаваемый ботом TrueConf (раздел 20 п.11 — личность подтверждает уже аутентифицированный канал, не отдельная система паролей).
- **Источники событий** — `X-Source-Token` (раздел «Принятый риск» выше), идемпотентность и WORM дополнительно ограничивают ущерб от подмены.

## 3. Управление ролями

Две роли в LDAP-каталоге: `admins` (полный доступ к консоли) и `employees` (обычные сотрудники без доступа к управлению источниками и аудиту). Личный кабинет `/me/` дополнительно защищён персональным token, выдаваемым ботом TrueConf.

## 4. Защита данных

- Транспорт — HTTPS с HSTS (см. память проекта, миграция на `газвпол.рус`).
- Пароли пользователей платформа не хранит (см. раздел 1).
- Синтетические данные (раздел 18.8 спецификации) — реальных персональных/производственных данных в системе нет по построению.

## 5. Управление жизненным циклом учётных записей

Автоотключение при увольнении — раздел 1. Ручной реактивации нет по
умолчанию (осознанное решение: возврат доступа — отдельное
администраторское действие, а не автоматика).

## 6. LDAP/AD — детали реализации

Тестовый каталог `glauth` (docker-compose сервис `ldap`) с синтетическими
пользователями — раздел 18.8 (реальной AD у вымышленной компании нет и
быть не может). Два bind'а: служебная учётная запись ищет DN и `memberOf`
пользователя (username экранируется — `ldap.EscapeFilter`/
`escape_filter_chars` на обеих сторонах, Go и Python — защита от LDAP-
инъекции), затем bind под точным DN с паролем пользователя проверяет
пароль. См. `go-platform/internal/adminapi/auth.go`, `packages/common/
ldap_auth.py`, `ldap/glauth.cfg`. Порт LDAP биндится на `127.0.0.1` —
недоступен снаружи хоста. **Остаточный риск**: трафик до самого LDAP-
контейнера внутри docker-сети идёт по `ldap://` (не `ldaps://`) —
приемлемо при текущей закрытости сети, кандидат на `ldaps://` при
расширении периметра.

## 7. Мониторинг и аудит

`/app/audit` (admin-only) — отказы входа, изменения источников, подписки/
отписки, автоотключения. `/app/` — операционный мониторинг платформы
(раздел «Инфраструктура», `INFRASTRUCTURE.md`). Оба — реальные, а не
макеты, проверены вживую.

## 8. История изменений — Redpanda/ClickHouse/MinIO

Побочный контур для карточек объекта/сотрудника и low-code поиска
(`internal/changelog`, `INFRASTRUCTURE.md` разделы 6-7) — не участвует
в критическом пути приёма/доставки (шлюз не импортирует этот пакет).
Все три сервиса опубликованы только на `127.0.0.1` хоста — проверено
внешним сканом с публичного IP, все пять портов (`19092`, `8123`,
`9010`, `9002`, `9003`) дают `Connection refused`. Low-code поиск
(`POST /api/change-history/search`) — whitelist полей вместо прямой
интерполяции в ClickHouse-запрос (`internal/changelog/query.go`),
значения только через именованные параметры; проверено вживую
попыткой передать SQL-инъекцию в имени поля — `422`, не 500 и не
исполнение постороннего SQL.

## 9. Формальная таблица: угроза → мера → реализация → тест → остаточный риск

Построена этим аудитом (2026-08-10) как отдельный проверяемый
деливерабл поверх разделов 1–8 выше — каждая строка подтверждена
прямым чтением кода и, где возможно, живым тестом в рамках этой же
сессии аудита.

| Угроза | Заявленная мера | Где реализована | Каким тестом подтверждена | Остаточный риск |
|---|---|---|---|---|
| Обход LDAP/AD-логина | Bind под точным DN пользователя, пароль платформа не хранит | `go-platform/internal/adminapi/auth.go`, `packages/common/ldap_auth.py` | `server_test.go` (unit) + живой логин `admin1`/`tester` через `/api/auth/login` (2026-08-10, `200`) | LDAP-трафик внутри docker-сети — `ldap://`, не `ldaps://` (см. ниже) |
| Смешение ролей admins/employees | Группа `admins` в LDAP-каталоге проверяется отдельно от факта успешного bind | `auth.go` — проверка `memberOf` после bind | Ручная проверка: `tester` (employees) получает `403` на `/api/sources`, `/api/audit` | нет |
| Кража/подмена session-cookie | HttpOnly + SameSite=Lax + Secure (когда `SESSION_COOKIE_SECURE=true` за HTTPS) | `auth.go:190-199` | `server_test.go:83` — assert `HttpOnly` и `SameSite` на выданной cookie | Secure-флаг зависит от корректной установки `SESSION_COOKIE_SECURE` в продовом `.env` — не включён по умолчанию (демо может идти по HTTP) |
| Угадывание чужого личного кабинета | Access-токен выдаётся ботом только в ответ на сообщение ОТ этого TrueConf-логина; сравнение constant-time | `internal/adminapi/personal.go:108`, `services/delivery_trueconf/handlers.py` | Прямое чтение `subtle.ConstantTimeCompare` на пути валидации токена | Токен бессрочный (нет истечения) — компенсируется тем, что его получение требует контроля над самим TrueConf-аккаунтом |
| Подмена/спам источника событий (`X-Source-Token`) | Токен на регистрацию, `subtle.ConstantTimeCompare`, обязателен для ВСЕХ источников | `internal/gateway/http.go:56` | **Живой тест 2026-08-10**: реальный существующий источник `zbx-brd-noyabrsk-01` — без токена `401`, с неверным токеном `401`, с верным — `202` и полный проход по конвейеру | mTLS/IP allow-list не реализован (пилотный периметр, см. `GO-MIGRATION.md` «Открытые расхождения») |
| Timing-атака на сравнение токенов/паролей | `subtle.ConstantTimeCompare` вместо `==` | Три независимых места: `auth.go:240`, `personal.go:108`, `gateway/http.go:56` | Прямое чтение кода — все три пути токен-сравнения используют constant-time, не нашлось ни одного `==`-сравнения секрета | нет |
| Подбор пароля (brute-force) | Rate limiter: 5 неудачных попыток / 5 минут на логин, сброс при успехе | `auth.go:112-154` (`loginLimiter`, `loginMaxAttempts=5`) | Юнит-покрытие лимитера в `auth.go`-тестах | Лимит по логину, не по IP — распределённый brute-force с разных логинов не замедляется этим механизмом (низкий риск при 87 пользователях пилота) |
| LDAP-инъекция через поле логина | Экранирование фильтра на обеих сторонах | Go: `ldap.EscapeFilter`; Python: `escape_filter_chars` (`packages/common/ldap_auth.py`) | Прямое чтение — оба клиента экранируют пользовательский ввод перед подстановкой в LDAP-фильтр | нет |
| Доступ уволенного сотрудника сохраняется | Периодическая сверка LDAP, автоотключение подписок + запись в `audit_log` | `services/deprovision/main.py` → `packages/common/deprovision.py`, цикл 30с | Живой тест (память проекта): `noc1` помечен уволенным в LDAP → подписки деактивированы в течение цикла, событие в `/console/audit` | Реактивации нет по умолчанию (осознанно — раздел 5 выше) |
| Перехват трафика до консоли | HTTPS с HSTS на публичном домене | `/etc/nginx/sites-available/dispatcher-https.conf` (VM) | **Живая проверка 2026-08-10**: `curl -sI https://xn--80aebrvrg.xn--p1acf/console/` → заголовок `Strict-Transport-Security: max-age=31536000; includeSubDomains` присутствует | Сертификат/домен — не часть кода репозитория, вне зоны ответственности приложения |
| Утечка данных алертов во внешние облачные AI API | Только локальный self-hosted Ollama | `packages/ai/`, `internal/pipeline/ai.go`, `internal/planner/ollama.go` | Grep по всему рантайм-коду (Go+Python) на предмет вызовов OpenAI/Anthropic/иных внешних SDK — ни одного обращения за пределы `OLLAMA_URL` | нет |
| Бесследное изменение/удаление истории алертов | `Signal` — WORM-таблица, приложение никогда не делает UPDATE/DELETE над ней | Схема `database/migrations/0000_baseline.sql` + grep по всему коду на `UPDATE signals`/`DELETE FROM signals` — ноль совпадений | Полнотекстовый grep по репозиторию (эта сессия) | нет |
| Отсутствие следа административных действий | `audit_log` — входы, изменения источников, подписки/отписки, автоотключения | `/console/audit`, `internal/adminapi/audit.go` | Живой просмотр журнала после тестовых действий этой же сессии | нет |

**Честно про то, что НЕ реализовано** (пилотные ограничения, не
скрываются): mTLS и IP allow-list для `POST /api/v1/ingest/raw` —
единственная защита источников сегодня токен + идемпотентность + WORM;
LDAPS (TLS до самого LDAP-каталога) — трафик `ldap://` внутри
изолированной docker-сети, не `ldaps://`. Оба — явно названы следующим
шагом для контура за пределами демонстрационного пилота, ни в одном
документе проекта не заявлены как готовые.

**Отдельно проверено этим аудитом**: устаревший Python-код
аудит-журнала в `services/api/main.py` — не подключён ни к одному
сервису `docker-compose.yml` (сервис `api` в Compose отсутствует),
не выполняется в проде; реальный путь аудита — исключительно Go
(`internal/adminapi/audit.go`), см. `GO-MIGRATION.md`.
