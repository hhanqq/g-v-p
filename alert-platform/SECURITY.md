# Диспетчер — безопасность: угрозы и меры

Критерий кейса «Информационная безопасность» — перечень актуальных угроз
и соответствующих технических мер. Все меры ниже реализованы и проверены
вживую (не только описаны), кроме явно помеченных как принятый риск.

## 1. Модель угроз

| Угроза | Вектор | Мера |
|---|---|---|
| Несанкционированный доступ к админ-функциям | Прямой запрос к SPA/API источников и аудита без сессии | LDAP/AD bind + подписанная HttpOnly session-cookie + проверка группы `admins` — раздел 6 ниже |
| Компрометация чужих подписок | Угадывание чужого TrueConf-логина в URL личного кабинета | Access-токен, выдаваемый только ботом в ответ на сообщение ОТ этого логина в TrueConf (личность подтверждает сам канал, не URL) — `services/delivery_trueconf/handlers.py` и Go `adminapi/personal.go` |
| Утечка пароля пользователя | Хранение пароля в БД платформы | Платформа пароль вообще не хранит и не видит — только LDAP/AD знает и проверяет пароль (`ldap_auth.authenticate`, bind под точным DN пользователя) |
| Компрометация API интеграции источников | Подмена/спам через `POST /api/v1/ingest/raw` | Идемпотентность по `(source_instance, hash)`, WORM-запись (раздел И3). Плюс токен-аутентификация: каждый источник, зарегистрированный через раздел «Источники», получает `api_token`, обязательный заголовком `X-Source-Token` (`go-platform/internal/gateway/http.go`, `subtle.ConstantTimeCompare`); все источники пилота (все 9 зарегистрированных инстансов на демо-стенде, 2026-08-09) защищены. **Остаточный, осознанный риск**: полный mTLS/allow-list по IP не реализован — следующий шаг для продакшн-периметра за пределами пилота. |
| Подбор пароля (brute-force) | Многократные попытки входа в `/api/auth/login` | Rate limiter на логин — не более 5 неудачных попыток за 5 минут на один логин, сброс при успешном входе (`go-platform/internal/adminapi/auth.go`) |
| Продолжение доступа уволенного сотрудника | Подписки остаются активными после увольнения | Автоотключение подписок при сверке с LDAP-каталогом (`packages/common/deprovision.py`), ~30с цикл, живьём проверено (см. память проекта — «уволенный» `noc1` корректно деактивирован) |
| Утечка данных во внешние облака | Передача содержимого алертов сторонним AI-API | ИИ-модуль — локальный self-hosted Ollama (`packages/ai/`), обращений к внешним облачным LLM нет нигде в коде |
| Timing-атака на сравнение токенов | Побайтовое сравнение `access_token` | `subtle.ConstantTimeCompare()` в Go token-based handlers |
| Отказ ИИ-компонента как вектор отказа в обслуживании | Недоступность/таймаут Ollama блокирует основной поток | Раздел И5 применён во всех 5 ИИ-сценариях: сбой ИИ никогда не блокирует и не роняет доставку/конвейер, только убирает необязательное дополнение |
| Бесследное изменение/удаление истории алертов | Прямой доступ к БД или баг приложения | `Signal` — WORM-таблица (раздел И3), приложение никогда не выполняет UPDATE/DELETE над ней |

## 2. Авторизация пользователей

- **Администраторы платформы** (`/app`, `/api/sources`, `/api/audit`) — LDAP/AD (см. раздел 6), группа `admins` для изменяющих и audit-функций.
- **Подписчики** (личный кабинет `/me/`) — токен, выдаваемый ботом TrueConf (раздел 20 п.11 — личность подтверждает уже аутентифицированный канал, не отдельная система паролей).
- **Источники событий** — `X-Source-Token` (раздел «Принятый риск» выше), идемпотентность и WORM дополнительно ограничивают ущерб от подмены.

## 3. Управление ролями

Две роли в LDAP-каталоге: `admins` (полный доступ к консоли) и `employees` (обычные сотрудники без доступа к управлению источниками и аудиту). Личный кабинет `/me/` дополнительно защищён персональным token, выдаваемым ботом TrueConf.

## 4. Защита данных

- Транспорт — HTTPS с HSTS (см. память проекта, миграция на `газвпол.рус`).
- Пароли пользователей платформа не хранит (см. раздел 1).
- Синтетические данные (раздел 18.8 спецификации) — реальных персональных/производственных данных в системе нет по построению.

## 5. Управление жизненным циклом учётных записей

Автоотключение при увольнении — раздел 1. Ручной реактивации нет по
умолчанию (осознанное решение: возврат доступа — отдельное
администраторское действие, а не автоматика).

## 6. LDAP/AD — детали реализации

Тестовый каталог `glauth` (docker-compose сервис `ldap`) с синтетическими
пользователями — раздел 18.8 (реальной AD у вымышленной компании нет и
быть не может). Два bind'а: служебная учётная запись ищет DN и `memberOf`
пользователя (username экранируется — `ldap.EscapeFilter`/
`escape_filter_chars` на обеих сторонах, Go и Python — защита от LDAP-
инъекции), затем bind под точным DN с паролем пользователя проверяет
пароль. См. `go-platform/internal/adminapi/auth.go`, `packages/common/
ldap_auth.py`, `ldap/glauth.cfg`. Порт LDAP биндится на `127.0.0.1` —
недоступен снаружи хоста. **Остаточный риск**: трафик до самого LDAP-
контейнера внутри docker-сети идёт по `ldap://` (не `ldaps://`) —
приемлемо при текущей закрытости сети, кандидат на `ldaps://` при
расширении периметра.

## 7. Мониторинг и аудит

`/app/audit` (admin-only) — отказы входа, изменения источников, подписки/
отписки, автоотключения. `/app/` — операционный мониторинг платформы
(раздел «Инфраструктура», `INFRASTRUCTURE.md`). Оба — реальные, а не
макеты, проверены вживую.
