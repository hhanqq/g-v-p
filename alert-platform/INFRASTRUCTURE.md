# Диспетчер — инфраструктура и масштабируемость

Критерий кейса «Инфраструктура и масштабируемость решения» — все цифры
ниже измерены на реальном развёртывании (VM, 90.156.217.61 /
xn--80aebrvrg.xn--p1acf), не оценены на глаз.

## 1. Пропускная способность (измерено вживую, 2026-08-07)

Полный прогон синтетического датасета через реальный шлюз → воркер →
резолвер → коррелятор → приоритизацию → доставку в TrueConf (включая
все 5 ИИ-сценариев, `packages/ai/`, работающие на этом же прогоне):

| Показатель | Значение |
|---|---|
| Объём прогона | 5302 сообщения |
| Приём (шлюз, запись в WORM+очередь) | 225 событий/с |
| Полная обработка конвейером (парсинг → доставка, 1 реплика воркера) | 2095 с на 5302 события ≈ **2,5 события/с** |
| Успешный разбор | 100% (5330/5331 событий; 1 намеренно «грязное» сообщение из синтетики) |
| Резолвинг объекта (не карантин) | 99,9% |
| Доставка уведомлений | 100% (3489/3489) |
| Инцидентов сформировано корреляцией | 112 |
| Средний MTTR | 163,7 с (≈ 2,7 мин, синтетические данные) |

**Целевая нагрузка кейса** — 5400 событий/сутки ≈ 0,0625 события/с в
среднем. Измеренные 2,5 события/с на **одной** реплике воркера дают
запас **более чем в 40 раз** относительно целевой средней нагрузки —
и это с учётом реальных сетевых вызовов к локальной LLM для
классификации/дедупликации, не идеализированный синтетический тест.
Пиковая нагрузка (не среднесуточная) при необходимости покрывается
горизонтальным масштабированием `pipeline-worker` (см. п.3).

## 2. Отказоустойчивость

| Механизм | Реализация |
|---|---|
| Недопущение потери событий | `Signal` — WORM-таблица (раздел И3): запись до разбора, разбор может упасть, событие — никогда |
| Идемпотентность приёма | Уникальность `(source_instance, hash)` — повтор от источника не создаёт дубль |
| Fault-изоляция воркера | Двухфазный `claim`/`process` (`FOR UPDATE SKIP LOCKED`) — ошибка на одном сообщении не топит батч и не роняет процесс (`go-platform/internal/pipeline`) |
| Восстановление после краха воркера | Go sweep возвращает зависшие `processing`-записи в очередь по TTL; `processed_at` ставится уже при claim, поэтому восстанавливается и падение до начала process |
| Надёжность доставки | `Notification` и `DeliveryOutbox` создаются одной транзакцией до вызова TrueConf; consumer использует `SKIP LOCKED`, retry/backoff и возврат зависших `processing` по TTL |
| Деградация ИИ-компонентов | Раздел И5, применено во всех 5 сценариях `packages/ai/`: сбой/таймаут LLM никогда не блокирует конвейер, только убирает необязательное дополнение |
| Резервное копирование БД | Ежедневный `pg_dump` (cron, 03:00, ротация 7 дней) — `~/pg_backup.sh` / `~/pg_restore.sh` на сервере, проверено вживую (пробный бэкап и восстановление отработали) |
| Резервирование PostgreSQL | Асинхронная физическая streaming-реплика (`postgres-replica`, `ops/postgres-replica/entrypoint.sh`) — измерено вживую 2026-08-10: `replay_lag` **0,591 мс**, `pg_is_in_recovery()` = true, тестовая запись через реальный `POST /api/v1/ingest/raw` на primary видна на реплике мгновенно (сверено по id строки в обеих БД) |

Резервирование PostgreSQL реализовано (см. строку выше) — реплика
только на чтение, ничто в приложении её не запрашивает в обычной
работе (не read-scaling, а именно резервная копия для критерия
«отказоустойчивость»). **Честно, осознанно не реализовано**: автоматический
failover/promotion (Patroni/repmgr) — переключение на реплику сегодня
ручное (`pg_ctl promote`), это следующий шаг, не заявляем его готовым;
multi-region — избыточно для пилота на 87 пользователей (кейс,
«пилотный периметр»).

**Как поднято, без даунтайма primary** (проверено вживую): роль
`replicator` создана живым `CREATE ROLE` (без рестарта), строка в
`pg_hba.conf` дописана и применена через `pg_reload_conf()` (reload,
не restart — при некорректной строке Postgres продолжает работать на
последнем валидном наборе правил), сама реплика поднята через
`pg_basebackup -R` с отдельного пустого volume. Устойчивость к
будущему чистому передеплою — идемпотентные `docker-entrypoint-initdb.d/`
скрипты (`database/initdb/`), исполняются только при инициализации
пустого тома primary, не трогают уже работающий инстанс. Измеренный
footprint реплики: **19 МиБ RSS, 0,01% CPU** (`docker stats`, простой).

## 3. Масштабируемость

- **pipeline-worker** — горизонтально: несколько реплик безопасно
  конкурируют за очередь (`FOR UPDATE SKIP LOCKED`), проверено логикой
  claim/process, не требует изменений кода для запуска N реплик.
- **Источники** — регистрация нового инстанса через `/sources/` (раздел
  4.3/11.2), подхватывается воркером без перезапуска в течение ~30с.
- **Каналы доставки** — `delivery-trueconf` изолирован версионированным
  `DeliveryCommand v1` и таблицей `delivery_outbox`; второй канал — новая
  реализация consumer/producer контракта без изменений конвейера.

## 4. Ресурсы под ИИ-модуль

Ollama развёрнута на том же сервере, что и остальной стек (совместное
использование GPU — демо-масштаб; для продакшена на 87+ пользователей
рекомендуется вынести на отдельный сервер/GPU, раздел «Дополнительные
вводные данные» кейса уже предполагает этот шаг: *«потребует выделения
двух серверов с GPU… увеличит смету»*). Технически ИИ-модуль уже
изолирован программно — Go и Python клиенты используют один HTTP-контракт,
который можно перенаправить на удалённый Ollama
одной переменной окружения (`OLLAMA_URL`), без изменения кода сценариев.

## 5. Мониторинг и аналитика платформы

`/console/app/` (раздел 7 кейса «Аналитика») — нагрузка очереди,
% успешного разбора, % резолвинга, % доставки, число ИИ-дополнений,
открытые проблемы/инциденты, MTTR, задержка обработки; автообновление
15с. `/console/api/metrics` — тот же снимок в JSON для внешних систем
мониторинга самой платформы.

**Живой пример находки через мониторинг**: тот же прогон, что дал цифры
из п.1, выявил при первой версии метрики MTTR аномалию — отрицательное
среднее время восстановления, из-за смешения меток времени двух разных
тестовых сессий в демо-БД (не ошибка конвейера, артефакт демо-данных).
Метрика дашборда защищена от таких строк (`services/api/metrics.py`,
`resolved_at >= opened_at`) — сам факт, что дашборд позволил это
заметить и починить за один проход, и есть демонстрация его пользы.

## 6. История изменений: Redpanda + ClickHouse (добавлено 2026-08-10)

Раздел «История изменений» (карточки объектов/сотрудников + low-code
поиск по событиям) добавляет Redpanda (Kafka-совместимая шина для
потока `change_events`) и ClickHouse (аналитическое хранилище для
поиска) как **строго побочный** контур: не встают между шлюзом и
`pipeline-worker`, не влияют на цифры п.1. Redpanda выбрана вместо
классического Kafka+ZooKeeper — тот же протокол и Go-клиент, но один
процесс без JVM, меньше нагрузки на ту же VM.

Измерено сразу после поднятия обоих сервисов (`docker stats`,
2026-08-10, простой):

| Сервис | CPU | Память | Лимит |
|---|---|---|---|
| Redpanda | 0,34% | 184 МиБ | 1 ГиБ (`mem_limit`) |
| ClickHouse | 9,74% (разовый старт) | 150 МиБ | 1 ГиБ (`mem_limit`) |

Хост (та же VM, что несёт остальные 11 сервисов): 16 vCPU, 62 ГиБ RAM,
58 ГиБ свободно на момент измерения — добавление обоих сервисов
укладывается в наблюдаемый запас с большим отрывом, лимиты по памяти
(`mem_limit: 1g` на каждый) защищают Postgres/Ollama от вытеснения при
аномальном росте одного из новых сервисов.

**changelog-worker** (Postgres→Kafka relay + Kafka→ClickHouse consumer,
один Go-процесс) — измерено под лёгкой реальной нагрузкой,
2026-08-10: **5,5 МиБ RSS, 0,08% CPU** — на порядок меньше Redpanda/
ClickHouse, соответствует измеренному ранее профилю остальных Go-
бинарей проекта (`PYTHON_VS_GO.md`). Сквозная задержка «мутация в
Postgres → строка видна в ClickHouse» измерена вживую: **~6 секунд**
на тестовой правке группы (при `CHANGELOG_POLL_INTERVAL_S=2`) — не
влияет ни на приём событий, ни на доставку уведомлений, только на
задержку появления записи в low-code поиске.

## 7. Data Lake: MinIO (фаза 5, добавлено 2026-08-10)

Опциональный сырой архив `Signal` (та же WORM-таблица, раздел И3, но
здесь для долгосрочного хранения/переобработки/ML/RAG, не для
операционного пути) — `changelog-worker` получил третий, полностью
необязательный поток: вотермарк-tailer читает `signals` СНАРУЖИ
gateway-процесса (`data_lake_watermark`, отдельная таблица-закладка —
`signals` как WORM никогда не получает UPDATE) и пишет NDJSON-батчи в
MinIO под `raw/YYYY/MM/DD/<from_id>-<to_id>.ndjson`.

**Проверено вживую, критическая проверка отказоустойчивости**:
`docker stop` на MinIO во время активной архивации → `POST
/api/v1/ingest/raw` продолжает отвечать `202` без единой заминки (шлюз
не импортирует пакет `changelog` и не знает о существовании MinIO);
`changelog-worker` не падает, тик архивации логирует ошибку соединения
и повторяет попытку; `docker start` на MinIO → тайлер сам
восстановился на следующем тике и продолжил ровно с того же батча
(`7501-8000.ndjson`), без потери и без дублирования данных —
водяной знак коммитится в той же транзакции, что и чтение диапазона.

Измерено (`docker stats`, под реальной нагрузкой архивации): MinIO —
230 МиБ/512 МиБ (`mem_limit`), 0% CPU в простое; `changelog-worker`
целиком (все три потока) — 8,6 МиБ RSS, <1% CPU.
