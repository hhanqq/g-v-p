# Архитектура стриминговой платформы управления оповещениями

Нужно реализовать backend-архитектуру платформы управления оповещениями для крупной промышленной компании.

Главная идея системы:
- принимать события из разных систем мониторинга;
- приводить их к единому формату;
- обогащать контекстом;
- удалять дубли;
- коррелировать связанные события;
- объединять их в инциденты;
- определять вероятный первоисточник проблемы;
- маршрутизировать уведомления только нужным сотрудникам;
- отправлять уведомления и AI-сводки в TrueConf;
- хранить историю событий и использовать её для аналитики и RAG.

---

## 1. Источники событий

Система должна уметь принимать события от:

- Zabbix
- SolarWinds
- Prometheus
- SCADA / АСУ ТП
- других систем

Новые источники должны подключаться без изменения основного ядра платформы.

Для этого используется слой:

`Adapters / Vector`

Его задача:
- получить исходное событие;
- определить источник;
- привести транспортный формат к внутреннему;
- передать событие дальше в Kafka.

---

## 2. Kafka

После adapters все события поступают в Kafka.

Kafka является центральной шиной событий.

Основной поток:

`Sources -> Adapters / Vector -> Kafka -> Stream Processing`

Kafka также используется для развязки источников и обработчиков, чтобы временное падение downstream-компонентов не приводило к потере события.

От Kafka также отдельно сохраняем данные в Data Lake.

---

# 3. Stream Processing на Go

Основной real-time pipeline реализуется на Go.

Последовательность обработки:

`Normalizer -> CMDB Enricher -> Deduplicator -> Correlation Engine -> Incident Manager -> Router / Subscribers`

## Normalizer

Приводит разноформатные события к единой модели.

Пример:

```json
{
  "event_id": "uuid",
  "source": "zabbix",
  "timestamp": "...",
  "site_id": "...",
  "object_id": "...",
  "component_id": "...",
  "event_type": "...",
  "severity": "P1",
  "message": "...",
  "attributes": {}
}
```

Оригинальное событие при этом нельзя терять.

---

## CMDB Enricher

Обогащает событие информацией об инфраструктуре.

Например:

`component -> object -> service -> site -> owner`

Добавляем:

- площадку;
- филиал;
- сервис;
- объект;
- компонент;
- IP / подсеть;
- организацию-владельца;
- ответственных сотрудников;
- критичность объекта;
- связи объектов.

---

## Deduplicator

Убирает информационный шум от повторяющихся событий.

Например:

30 одинаковых событий:

`host unreachable`

не превращаются в 30 уведомлений.

Сами события сохраняются, но для дальнейшей обработки могут быть представлены как один логический алерт с количеством повторений.

Fingerprint можно строить из:

`source + object_id + component_id + event_type + severity`

---

## Correlation Engine

Связывает события между собой.

Корреляция происходит по конфигурируемым правилам.

Учитываются:

- временное окно;
- объект;
- компонент;
- площадка;
- сервис;
- подсеть;
- тип события;
- критичность;
- CMDB-зависимости;
- плановые работы;
- другие атрибуты.

Например:

```text
10:00:00 power_loss
10:00:04 router_down
10:00:10 server_unreachable
10:00:20 application_unavailable
```

могут быть объединены в один инцидент.

Correlation Engine не должен жёстко хардкодить все связи.

Правила хранятся в PostgreSQL и должны изменяться из административного интерфейса.

---

## Incident Manager

Создаёт и ведёт инциденты.

Инцидент содержит:

- ID;
- статус;
- критичность;
- площадку;
- объект;
- связанные события;
- предполагаемый первоисточник;
- root cause score;
- ответственных;
- время открытия;
- время восстановления;
- время закрытия.

Статусы:

`new -> acknowledged -> in_progress -> recovered -> closed`

Исходные уведомления не редактируются задним числом.

Дополнительная информация формируется как новые события:

- новое;
- дополнение;
- повтор;
- эскалация;
- восстановление;
- закрытие.

---

## Router / Subscribers

Определяет получателей уведомления.

Учитывает:

- подписки;
- роль;
- сервис;
- объект;
- площадку;
- критичность;
- владельца;
- график дежурств.

Например:

P0 по конкретной буровой может быть отправлен только:

- старшему механику участка;
- руководителю актива;

вместо массовой рассылки сотням сотрудников.

---

# 4. PostgreSQL

PostgreSQL используется как основное operational/business storage.

Redis в текущей версии архитектуры не используется.

PostgreSQL хранит:

- incidents;
- active incident state;
- correlation rules;
- routing rules;
- users;
- subscriptions;
- owners;
- services;
- objects;
- components;
- notification state;
- audit metadata.

Также PostgreSQL хранит состояние активных correlation windows.

Например:

```text
incident_id
site_id
object_id
status
correlation_until
root_event_id
```

Причина отказа от Redis:

текущая нагрузка не требует отдельного in-memory state store, а Redis увеличивает эксплуатационную сложность.

Если в будущем нагрузка вырастет, Redis можно добавить как optimization/cache layer без изменения основной бизнес-логики.

---

# 5. ClickHouse

ClickHouse используется как hot analytical/event storage.

Он хранит большой поток нормализованных событий.

Используется для:

- быстрого поиска событий;
- истории объектов;
- аналитики;
- dashboard;
- подсчёта шума;
- MTTR;
- количества инцидентов;
- статистики корреляции;
- анализа источников.

ClickHouse НЕ используется как основное mutable-хранилище состояния инцидента.

То есть:

`PostgreSQL = operational state`

`ClickHouse = event history + analytics`

---

# 6. Data Lake

Из Kafka сырые и нормализованные данные также сохраняются в Data Lake.

Пример структуры:

```text
Data Lake
├── raw
├── normalized
└── archive
```

Data Lake нужен для:

- долгосрочного хранения;
- повторной обработки данных;
- исторического анализа;
- ML;
- RAG;
- расследования инцидентов.

В качестве Data Lake может использоваться S3-compatible storage / MinIO.

---

# 7. Spark

Spark не находится в основном real-time path.

Он является Stage 2 и используется только для offline analytics / ML.

Схема:

`Data Lake -> Spark`

Spark можно использовать для:

- обработки большого объёма истории;
- подготовки ML-признаков;
- анализа старых инцидентов;
- поиска статистических закономерностей;
- подготовки данных для моделей.

Основной поток алертов работает без Spark.

---

# 8. AI / RAG module

Отдельный AI/RAG-модуль выполняет четыре основные функции:

1. Summary / авто-сводка.
2. Оценка инцидента.
3. Оценка вероятного первоисточника / root cause score.
4. Рекомендации из базы знаний.

AI получает контекст инцидента после нормализации, CMDB enrichment и correlation.

Пример входного контекста:

```json
{
  "incident": {},
  "events": [],
  "object": {},
  "dependencies": [],
  "rules": [],
  "history": []
}
```

AI не должен самостоятельно скрывать критические события или принимать необратимые решения.

Он является advisory-компонентом.

---

# 9. Root cause score

AI оценивает вероятность того, что конкретное событие является первоисточником цепочки.

Пример:

```json
{
  "candidate_event_id": "event-123",
  "root_cause_score": 0.87,
  "reason": "событие произошло первым и объясняет отказ связанных компонентов"
}
```

Оценка возвращается в Incident Manager.

Важно:

это не абсолютная истина, а вероятность / рекомендация.

---

# 10. База знаний и RAG

AI использует RAG.

База знаний содержит:

- статьи;
- runbook;
- инструкции;
- postmortem;
- FAQ;
- описание прошлых инцидентов;
- рекомендации инженеров.

Отдельно существует:

`Vector DB / RAG Index`

В нём хранятся embeddings документов.

Поток:

```text
Документы / исторические инциденты
        ↓
chunking
        ↓
embeddings
        ↓
Vector DB
        ↓
retrieval
        ↓
LLM
```

При анализе инцидента AI ищет релевантные инструкции и предыдущие похожие случаи.

---

# 11. AI summary для TrueConf

AI формирует короткую понятную сводку.

Например вместо 20 технических алертов:

```text
P0: потеря связи с площадкой Север-3.

Вероятная причина:
сбой электропитания.

Затронуто:
- 12 серверов;
- сетевое оборудование;
- система управления насосами.

Ответственный:
дежурный энергетик.

Рекомендуемая проверка:
проверить питание распределительного шкафа №4.
```

Эта сводка отправляется в TrueConf.

---

# 12. TrueConf

TrueConf является каналом доставки уведомлений пользователям.

Через TrueConf отправляются:

- новые инциденты;
- эскалации;
- дополнения;
- AI-summary;
- восстановление;
- закрытие;
- пользовательские дайджесты.

TrueConf не является основным хранилищем событий.

История хранится внутри платформы.

---

# 13. Audit Log

Нужно вести отдельный audit log.

Логировать:

- изменение correlation rule;
- изменение routing rule;
- изменение подписок;
- изменение ролей;
- принятие инцидента;
- передачу инцидента;
- закрытие;
- действия администратора;
- действия пользователя;
- автоматические решения платформы.

Формат:

```json
{
  "timestamp": "...",
  "actor_id": "...",
  "actor_role": "...",
  "action": "...",
  "resource_type": "...",
  "resource_id": "...",
  "before": {},
  "after": {},
  "result": "success"
}
```

Audit log должен быть append-only.

---

# 14. Monitoring

Для мониторинга самой платформы использовать:

`Prometheus + Grafana`

Следить за:

- Kafka consumer lag;
- количеством событий;
- latency обработки;
- ошибками;
- состоянием Go workers;
- состоянием PostgreSQL;
- состоянием ClickHouse;
- доставкой TrueConf;
- временем AI inference;
- количеством unknown events;
- количеством открытых инцидентов.

```text

   ↓

   ├────────────────────────→ Data Lake
   │                              ↓
   │                         Spark Stage 2
   │
   ↓
Stream Processing (Go)
   ↓
Normalizer
   ↓

   ↓

   ↓

   ↓

```

# 16. Главный принцип архитектуры

Основной real-time поток должен оставаться максимально простым:

`Source -> Kafka -> Go -> Incident -> Routing -> TrueConf`

AI, RAG, Spark и аналитика не должны блокировать критический путь доставки P0/P1 уведомлений.

Если AI недоступен:

- инцидент всё равно создаётся;
- правила корреляции продолжают работать;
- маршрутизация работает;
- TrueConf получает обычное уведомление без AI-сводки.

Это обязательное архитектурное свойство системы.
