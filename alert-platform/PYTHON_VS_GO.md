# Диспетчер: Python vs Go — что и почему перенесено

Сравнение до/после миграции доменного ядра платформы с Python на Go
(2026-08-08). Все цифры ниже измерены на реальном развёртывании
(90.156.217.61 / газвпол.рус), не оценены на глаз — тот же принцип,
что и в `INFRASTRUCTURE.md`.

## TL;DR

| | Было (Python) | Стало (Go + Python-адаптер) |
|---|---|---|
| Приём событий, конвейер, планировщик доставки, сценарии/SLA, admin API | FastAPI/SQLAlchemy | Go (`go-platform/`) |
| TrueConf-интеграция (vendor SDK, входящие команды, физическая отправка) | Python | Python (осознанно оставлено) |
| Схема БД | `Base.metadata.create_all()` при старте | Последовательные SQL-миграции с трекингом |
| Размер образа сервиса | ~348 МБ | 32–56 МБ |
| Память в рантайме на сервис | 44–68 МБ | 3–9 МБ |
| Тестов | 166 (pytest) | 44 (go test) + 166 (pytest на оставшемся Python) |
| Таблиц в БД | 22 | 23 (+`delivery_outbox`) |

## 1. Архитектура: было / стало

| Компонент | Было | Стало | Файлы (Go) |
|---|---|---|---|
| Приём событий (gateway) | `services/gateway/main.py`, FastAPI | Go, тот же HTTP-контракт | `internal/gateway/` |
| Конвейер: parser → resolver → state → correlator → priority | `services/pipeline/worker.py` + `packages/rules`, `packages/models` | Go, тот же алгоритм | `internal/pipeline/` |
| Маршрутизация уведомлений, шаблоны, сценарии/SLA, LLM-вызовы | `services/delivery_trueconf/main.py` (747 строк, всё в одном файле) | Go planner, публикует `DeliveryCommand v1` в PostgreSQL outbox | `internal/planner/`, `internal/scenario/` |
| Admin API, LDAP-сессия, личный кабинет, страница текущих алертов | `services/api/main.py` + `app_api.py` | Go, отдаёт тот же React SPA | `internal/adminapi/` |
| TrueConf: vendor SDK, входящие команды (`/старт`, `/кабинет`, `/алерты`, `/сводка`, reply-ACK), физическая отправка | `services/delivery_trueconf/main.py` | **Осталось на Python** — `adapter.py`, `handlers.py`, `outbox.py` | — |
| Синтетическое демо, LDAP deprovision sweep | `services/api/main.py` (встроено) | Вынесено в изолированные Python-сервисы | `services/demo/`, `services/deprovision/` |

**Почему TrueConf остался на Python**: `python-trueconf-bot` — специализированная
библиотека, единственная рабочая интеграция с этим vendor SDK на момент
миграции. Переписывать её на Go ради унификации языка — не оправданный
риск для работающего канала доставки. Вместо этого Python-адаптер стал
**тонким**: не считает маршрутизацию, не строит текст уведомления и не
дёргает LLM — только выполняет уже готовую команду из outbox и
сохраняет `chat_id`/`message_id` обратно.

## 2. Контракт между Go и Python: outbox, а не прямой вызов

Раньше один и тот же Python-процесс решал «кому/что отправить» и
«отправлял» — маршрутизация, шаблон и физическая отправка были
неразделимы. Теперь между Go-ядром и Python-адаптером — таблица
`delivery_outbox` (PostgreSQL, `contracts/delivery-command-v1.schema.json`):

- Go planner одной транзакцией создаёт `Notification` + `delivery_outbox`
  строку с уже готовым текстом и `idempotency_key`.
- Python-адаптер забирает строки через `FOR UPDATE SKIP LOCKED`,
  отправляет через TrueConf API, пишет `chat_id`/`message_id` назад.
- Оба процесса можно останавливать/обновлять независимо; Python больше
  не может случайно продублировать бизнес-логику маршрутизации.

## 3. Модель данных и миграции

| | Было | Стало |
|---|---|---|
| Источник истины схемы | `packages/models/db.py` (SQLAlchemy), применялось `Base.metadata.create_all()` при старте каждого сервиса | `database/migrations/*.sql`, применяется один раз сервисом `migrate` |
| История изменений схемы | Не велась (ручные `ALTER TABLE` по памяти проекта, как в этой же сессии для `acknowledged_at`/`ScenarioRun`) | 7 пронумерованных, идемпотентных файлов, таблица `schema_migrations` |
| Применимость на уже заполненной БД | Аддитивные `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` вручную, каждый раз заново | `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` везде, безопасно на чистой и на существующей базе — **проверено вживую на реальной продовой БД с недельной историей** |

Таблиц: было 22, стало 23 (+`delivery_outbox`); `notifications` получила
колонку `recipient` (устойчивый идентификатор получателя — раньше был
только `chat_id`, который мутирует после отправки).

## 5. Пропускная способность

Раньше (`INFRASTRUCTURE.md`, измерено 2026-08-07, Python pipeline-worker,
1 реплика): **2,5 события/с** полной обработки (парсинг → резолвинг →
корреляция → приоритет → доставка), при целевой нагрузке кейса
0,0625 события/с — запас 40×.

Сейчас (2026-08-08, Go pipeline-worker, тот же сервер): измерено
напрямую по убыванию `queue_depth` за 60 секунд боевой обработки —
**10 488 → 10 388, то есть ≈1,7 события/с.**

**Честно: это медленнее задокументированной Python-цифры, и вот
почему не стоит делать из этого вывод «Go медленнее»:**
- В момент замера pipeline-worker разбирал историческую фикстуру
  (14 дней, ~13 000 сообщений, специально расширенную для более богатой
  аналитики) с повышенной долей «неоднозначных» корреляций — на каждую
  из них уходит синхронный вызов ИИ-гипотезы первопричины к Ollama.
- **В это же время** `delivery-planner` тоже дёргал ту же самую Ollama
  (для сводок/рекомендаций) — один GPU, одна модель, инференс
  сериализуется между двумя Go-сервисами одновременно. В оригинальном
  Python-замере от 2026-08-07 такой конкуренции за LLM не было.
- Это не чистый бенчмарк «Python vs Go на одинаковых условиях» — это
  честная цифра БЕЗ подгонки, которую не стоит замалчивать, но и
  нельзя использовать как прямое сравнение производительности языков.
  Сам конвейер (парсинг/резолвинг/корреляция/приоритет) в Go —
  без сомнения, быстрее по CPU-времени на сообщение (компилируемый код
  против интерпретатора); тормозит здесь общий сосед — Ollama, а не
  язык воркера.

## 6. Строк кода

Не самая содержательная метрика, но честности ради: Go-реализация
перенесённого ядра (`go-platform/`, без тестов) — **5470 строк**.
Эквивалентные по ответственности Python-модули (gateway, pipeline,
priority, routing, LDAP-сессия, сценарии, AI-клиенты) — **3842 строки**.
Go получился **длиннее** на ~42% — типично для статически типизированного
языка с явной обработкой ошибок (`if err != nil` на каждом шаге вместо
исключений); отрабатывает это увеличение объёма компилируемыми
гарантиями типов и меньшим рантайм-оверхедом, а не читаемостью.

## 8. Реальные проблемы, найденные при переносе на прод

Не найдены статическим анализом — вскрылись именно при разворачивании
на боевой, уже населённой неделями истории БД (то, ради чего вообще
стоит выкатывать на прод, а не только гонять тесты):

1. **Deadlock при миграции** — `ALTER TABLE problems` столкнулся с
   ещё работающим старым Python pipeline-worker, доедавшим бэклог.
   Решение: старые сервисы, чьи локи держат таблицу, останавливаются
   до миграции, не после.
2. **Гонка на границе переключения** — старый Python-поток успел
   отправить пару уведомлений ровно в момент cutover, новый Go-planner
   независимо создал дубли для тех же проблем → упал на уникальном
   ограничении, уронив Python-адаптер. Разобрано вручную: 13 настоящих
   дублей удалено, 18 легитимных новых оставлено.
3. **Системный (не разовый) баг в `planner.createDelivery`** —
   проверка идемпотентности опиралась на `notifications.chat_id`,
   который Python-адаптер переписывает после отправки. Ломалась на
   *каждом* следующем тике для *любой* ещё не закрытой проблемы — не
   краевой случай миграции, а постоянный источник мусорных записей и
   шума в логах. Исправлено: проверка по стабильному ключу
   (problem+type+recipient) до вставок.
4. **Отсутствие изоляции сбоя после успешной отправки** в
   `outbox.py` — если запись результата уже отправленного сообщения
   падала, необработанное исключение роняло весь consumer, а на
   TTL-рестарте зависшая запись переигрывалась заново — то есть
   реальный человек мог получить **дубликат уже доставленного
   сообщения**. Исправлено try/except с терминальной пометкой `sent`
   без повторной отправки.

Оба системных бага (3, 4) исправлены в Go/Python коде, тесты добавлены,
задеплоено повторно — сейчас всё стабильно (проверено: 59 реальных
NEW/CLOSURE уведомлений за 90 секунд боевой нагрузки без единой ошибки).

## 9. Что сознательно НЕ тронуто

Из `GO-MIGRATION.md`, открытые расхождения — не забытые детали, а
явно отложенные решения:

- mTLS/HMAC, allow-list, rate limiting на gateway — есть строгая
  JSON-валидация и WORM+queue, но защита интеграционного API как
  отдельный этап.
- Канонический `POST /api/v1/events` не перенесён — используется
  универсальный `/api/v1/ingest/raw`.
- Полная семантика `взял`/`не мой`/`следствие` (раздел 9.4/M8) —
  reply-ACK уже фиксируется и используется Go-сценариями, но
  трёхвариантная маршрутизация ответов — отдельная будущая задача.

## Итог

Перенос ядра на Go — не переписывание ради переписывания: конкретные,
измеренные на этой же машине выгоды (в разы меньше памяти и размера
образа), при сохранении 1:1 бизнес-логики (проверено на реальных
исторических данных: та же корреляция, тот же приоритет, то же
ветвление сценариев). TrueConf сознательно остался на Python — там,
где Go не даёт выгоды и добавляет риск. Миграция на прод вскрыла два
реальных, небанальных бага в идемпотентности доставки — именно такие
находки оправдывают требование «проверять вживую, а не только в
тестах», которое проходит через весь проект.
