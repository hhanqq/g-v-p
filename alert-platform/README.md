# Диспетчер

[![CI](https://github.com/hhanqq/g-v-p/actions/workflows/ci.yml/badge.svg)](https://github.com/hhanqq/g-v-p/actions/workflows/ci.yml)

«Диспетчер» — платформа управления оповещениями об инцидентах для
промышленного мониторинга (кейс IT Camp: Zabbix + SolarWinds, пилот на
4 филиалах, 87 пользователей). Задача, которую она решает: сегодня
авария на объекте порождает шквал разрозненных SMS/звонков сотням
контактов, и драгоценное время уходит не на устранение, а на то,
чтобы понять, кто вообще должен реагировать. Диспетчер принимает
сырые события от систем мониторинга, нормализует и дедуплицирует их
(в том числе с помощью локальной ИИ-модели), коррелирует связанные
события в один инцидент, определяет приоритет и адресата по CMDB и
подпискам, и доставляет одно понятное сообщение в TrueConf нужному
человеку — с автоматической эскалацией, если тот не отреагировал.

Этот файл — инструкция для человека, который впервые открывает
репозиторий и должен запустить стенд и проверить, что заявленное в
презентации реально работает. Более глубокие документы, если нужно
провалиться в детали:

|---|---|

## Из чего состоит

Go — ядро конвейера и админ-панель; Python — только тонкий адаптер
TrueConf (внешний SDK) и вспомогательные скрипты (миграции, демо-сид,
`deprovision-worker`). Подробности — [`ARCHITECTURE.md`](ARCHITECTURE.md) §1.

| Компонент | Роль |
|---|---|
| `gateway` (Go) | Приём событий, `POST /api/v1/ingest/raw`, WORM-запись |
| `pipeline-worker` (Go) | Парсинг → резолвинг → свёртка → корреляция → приоритет |
| `delivery-planner` (Go) | Маршрутизация, сценарии, SLA, шаблоны, вызовы Ollama, outbox |
| `delivery-trueconf` (Python) | Тонкий адаптер: берёт готовую команду из outbox, отправляет через `python-trueconf-bot` |
| `delivery-email` (Go) | Второй канал доставки — тот же тонкий принцип, свой SMTP-адаптер на `delivery_outbox` (`channel='email'`) |
| `mailhog` | Демо-SMTP-катчер (реальный протокол + веб-просмотр писем на `:8025`); заменяется корпоративным SMTP через `.env` без пересборки |
| `admin-console` (Go + React SPA) | Веб-консоль, LDAP-сессия, личный кабинет |
| `postgres` / `postgres-replica` | Единственный источник правды + async streaming-реплика |
| `ldap` (GLAuth) | Демо-каталог сотрудников для LDAP/AD-логина |
| `ollama` (systemd, вне Compose) | Локальная LLM для 7 ИИ-сценариев |
| `deprovision-worker` (Python) | Периодическая сверка LDAP, автоотключение уволенных |
| `redpanda` + `clickhouse` + `minio` + `changelog-worker` (Go) | Строго побочный контур: история изменений, low-code поиск, архив |

## Prerequisites

- Docker Engine 24+ и Docker Compose v2 (`docker compose version`).
- 4+ vCPU, 8+ ГиБ RAM свободно для полного стека **без** реалистичной
  ИИ-модели. Сам стек (16 Go/Python-сервисов + Postgres + Redpanda +
  ClickHouse + MinIO) в простое занимает низкие сотни МиБ суммарно —
  измерено вживую, см. [`INFRASTRUCTURE.md`](INFRASTRUCTURE.md) §6-7.
- Для реалистичной работы ИИ-сценариев — Ollama с моделью класса
  `qwen3-coder`/30B (Q4_K_M) требует **~14 ГиБ VRAM** (на проде — Tesla
  T4, измерено). Без GPU такого объёма Ollama можно поднять на CPU
  (медленнее) или с меньшей моделью — это не сломает конвейер: раздел
  И5 гарантирует, что таймаут/ошибка ИИ не блокирует приём и доставку,
  просто уведомление уйдёт без ИИ-обогащения (проверено живым отказом
  Ollama, см. [`COMPLIANCE_MATRIX.md`](COMPLIANCE_MATRIX.md) критерий 3).
  Ollama **не входит** в `docker-compose.yml` — поднимается отдельно
  (systemd/Docker/любым способом) и указывается через `OLLAMA_URL`.
- Открытые порты (только если стенд разворачивается на удалённом
  хосте, а не `localhost`): **8081** (gateway, приём событий и
  `/docs`), **8090** (admin-console, веб-консоль). Всё остальное —
  PostgreSQL, LDAP, Redpanda, ClickHouse, MinIO — по умолчанию
  биндится на `127.0.0.1` и не должно быть открыто наружу (см.
  [`SECURITY.md`](SECURITY.md)).
- Реальный TrueConf Server нужен только для полной проверки живой
  доставки — см. «Режим без реального TrueConf» ниже, стенд полностью
  разворачивается и проверяется без него.

## `.env`

Скопируйте пример и правьте под себя:

```bash
cd alert-platform
cp .env.example .env
```

**По-настоящему обязательны только переменные TrueConf** — без них
`delivery-trueconf` не сможет авторизоваться на реальном сервере
(если сервис не запускать — см. режим ниже, — остальной стек это не
блокирует):

| Переменная | Назначение |
|---|---|
| `TRUECONF_SERVER` | Домен TrueConf-сервера компании |
| `TRUECONF_BOT_USERNAME` / `TRUECONF_BOT_PASSWORD` | Учётная запись бота (создаётся вручную в админ-панели TrueConf) |
| `TRUECONF_TEST_RECIPIENT` | TrueConf-логин тестового получателя (должен совпадать с одним из LDAP-пользователей — см. «Приложение: демо-доступы» в [`USER_GUIDE.md`](USER_GUIDE.md), иначе `deprovision-worker` его деактивирует) |

**Всё остальное имеет безопасные demo-значения по умолчанию** прямо в
`docker-compose.yml` (через `${VAR:-default}`) — трогать не
обязательно для проверки стенда:

| Переменная | Демо-значение | Когда менять |
|---|---|---|
| `POSTGRES_PORT` | `5433` | если порт занят другим процессом на хосте |
| `SESSION_SECRET` | демо-строка | обязательно сменить перед реальным продом |
| `SESSION_COOKIE_SECURE` | `false` | поставить `true`, когда стенд за HTTPS |
| `LDAP_SEARCH_USER` / `LDAP_SEARCH_PASSWORD` | `svc-search` / `svc123` | реальный AD/LDAP вместо демо-каталога |
| `CLICKHOUSE_PASSWORD`, `MINIO_ROOT_USER/PASSWORD`, `REPLICATOR_PASSWORD` | демо-пароли | при выходе за пределы пилотного периметра |
| `OLLAMA_MODEL` | `log-reader` | своё имя модели, если используете другую |
| `DELIVERY_DATABASE_URL` | тот же Postgres | обычно не требуется менять |

## Воспроизводимый запуск

### Режим без реального TrueConf (по умолчанию, для проверки стенда)

Оставьте `TRUECONF_*` из `.env.example` как есть (`change-me`) и не
поднимайте `delivery-trueconf` — весь остальной домен работает и
проверяется без него: события принимаются, разбираются, коррелируются,
маршрутизируются, уведомления доходят до `delivery_outbox` со
статусом `queued` (готовая команда `DeliveryCommand v1`, просто некому
её физически отправить в TrueConf). Это честно и осознанно — CLAUDE.md
прямо предупреждает, что поднимать `delivery-trueconf` без настоящих
`TRUECONF_*` бессмысленно (сервис не сможет авторизоваться и будет
падать в рестарт-цикл).

```bash
git clone <URL-репозитория>
cd alert-platform
cp .env.example .env

# Инфраструктура + миграции + полный стек, кроме delivery-trueconf —
# depends_on в docker-compose.yml сам выстраивает верный порядок
# (postgres → migrate → всё остальное), отдельно накатывать миграции
# не нужно.
docker compose up -d --build \
  postgres postgres-replica ldap \
  migrate kb-index \
  gateway pipeline-worker delivery-planner admin-console demo-runner \
  deprovision-worker redpanda clickhouse clickhouse-migrate minio changelog-worker \
  delivery-email mailhog
# (demo-runner — источник кнопок на /console/demo и живых AI self-test;
#  admin-console от него жёстко зависит через depends_on, так что даже
#  без явного перечисления Compose поднял бы его сам — здесь он назван
#  явно только для ясности команды)

# Демо-данные: оборудование/CMDB (идемпотентно, безопасно перезапускать)
DATABASE_URL=postgresql+psycopg2://alert:alert@localhost:5433/alert_platform \
    python3 scripts/seed_demo.py --seed 42

# Источники (Zabbix/SolarWinds инстансы с токенами) сеются
# АВТОМАТИЧЕСКИ при первом старте pipeline-worker из
# connectors/sources.yaml — отдельной команды не требуется.

# Демо-штат: 27 сотрудников с ролями/компетенциями/зонами ответственности
# + отпуска/больничные, влияющие на маршрутизацию (идемпотентно)
python3 scripts/seed_employees.py --url http://127.0.0.1:8090 --username admin1 --password admin123

# 4 демо-сценария на этом штате (Иванов в отпуске → резерв Петров;
# Волков на больничном → эскалация; параллельная доставка TrueConf+Email)
python3 scripts/seed_demo_scenarios.py --url http://127.0.0.1:8090 --username admin1 --password admin123 --activate

# Проверка живости
curl http://127.0.0.1:8081/api/v1/health
curl -I http://127.0.0.1:8090/           # SPA консоли

# UI
open http://127.0.0.1:8090/
```

### Полный режим с реальным TrueConf

Заполните `TRUECONF_SERVER`/`TRUECONF_BOT_USERNAME`/
`TRUECONF_BOT_PASSWORD`/`TRUECONF_TEST_RECIPIENT` реальными значениями
(бот заводится вручную в админ-панели TrueConf-сервера, `TRUECONF_TEST_RECIPIENT`
должен быть заведён и в LDAP-каталоге демо-стенда — см. таблицу
демо-доступов в [`USER_GUIDE.md`](USER_GUIDE.md)), затем добавьте
`delivery-trueconf` к тому же `docker compose up`:

```bash
docker compose up -d --build delivery-trueconf
```

С этого момента `delivery_outbox`-записи реально доходят до
TrueConf-чата получателя — то же самое можно проверить, отправив
боту `/старт` из реального клиента.

### Отправка тестового события и ожидаемый результат

```bash
# Токен источника — из /api/sources под LDAP-сессией администратора
curl -s -c /tmp/dispatcher_cookies.txt -X POST http://127.0.0.1:8090/api/auth/login \
  -H "Content-Type: application/json" -d '{"username":"admin1","password":"admin123"}' >/dev/null
TOKEN=$(curl -s -b /tmp/dispatcher_cookies.txt http://127.0.0.1:8090/api/sources \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['items'][0]['api_token'])")
SOURCE=$(curl -s -b /tmp/dispatcher_cookies.txt http://127.0.0.1:8090/api/sources \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['items'][0]['instance'])")

curl -X POST http://127.0.0.1:8081/api/v1/ingest/raw \
  -H "Content-Type: application/json" \
  -H "X-Source-Token: $TOKEN" \
  -d "{
        \"source_system\": \"zabbix\",
        \"source_instance\": \"$SOURCE\",
        \"raw_body\": \"PROBLEM: Input power lost on dc-01\\nHost: dc-01\\nSeverity: Disaster\\nTime: 2026.08.10 12:00:00\"
      }"
# -> {"signal_id": <N>, "status": "queued"}, HTTP 202
```

(пример предполагает первый источник в списке — реальная система
`zabbix`; если у неё другой набор объектов CMDB, замените `dc-01` на
любой объект, видимый в разделе «Оборудование» вашего стенда)

Ожидаемый результат в течение нескольких секунд (проверено вживую
2026-08-10, полный трейс — [`COMPLIANCE_MATRIX.md`](COMPLIANCE_MATRIX.md)
критерий 1): `signal_queue.status='done'` → новая строка в `problems`
(`symptom_class='power_lost'`, объект `brd-noyabrsk/dc-01` резолвлен
из CMDB) → строка в `notifications` (`type='NEW'`) → строка в
`delivery_outbox` (`status='queued'`, в полном режиме с TrueConf —
`'sent'`). Без токена или с неверным — `401`, без потери события
(WORM всё равно ничего не пишет мимо себя — токен проверяется до
самой записи).

## Как проверить, что всё работает (smoke-test проверяющего)

Пошагово, без знания внутренней архитектуры, ~10 минут:

1. **Health.** `curl http://<host>:8081/api/v1/health` → `200`.
2. **Вход в консоль.** Откройте `http://<host>:8090/`, войдите
   `admin1` / `admin123` (демо-LDAP, полный список — приложение
   [`USER_GUIDE.md`](USER_GUIDE.md)).
3. **Главная.** Увидите дашборд: очередь, % разбора/резолвинга/доставки,
   MTTR, открытые проблемы/инциденты — обновляется каждые 15с.
4. **Оборудование → карточка объекта.** Откройте любой объект
   (например `brd-noyabrsk/dc-01`) — паспорт + график связанных
   алертов.
5. **Сотрудники → карточка сотрудника.** Подписки + статус доступности
   (доступен/на смене/в отпуске и т.д., с датами начала-конца).
6. **Сценарии / SLA.** Откройте существующий сценарий — граф условие→
   уведомление→проверка→эскалация; откройте SLA-правила.
7. **Отправьте synthetic alert** — команда из раздела выше или кнопка
   на `/console/demo` (готовые кейсовые сценарии: каскад, P0-отказ
   питания и т.д., доставляют реальные уведомления за ~60с вместо
   реального времени эскалации).
8. **Проследите обработку** — `/console/alerts` (журнал сырых
   событий) → `/console/incidents` (сформированная проблема/инцидент)
   → если TrueConf настроен, сообщение придёт в чат бота получателю.
9. **Аналитика.** `/console/analytics` — событие из шага 7 уже
   отражено в статистике за период.
10. **Аудит.** `/console/audit` — сам факт вашего логина уже там.

Если что-то из этого не воспроизводится — это баг, а не ожидаемое
поведение; ни один пункт выше не завязан на реальный TrueConf.

## Обзор интерфейса

| Раздел | Назначение |
|---|---|
| **Главная** | Состояние конвейера прямо сейчас (очередь, доставка, MTTR) |
| **Инциденты** | Кластеры связанных проблем с общей первопричиной |
| **Алерты** | Журнал всех сырых событий от источников |
| **Оборудование** | Интерактивное дерево (филиал → категория → объект), раскрывается на месте, с поиском и агрегатами на каждом уровне |
| **Сотрудники** | Карточки: роль, компетенции, зона ответственности, каналы доставки, подписки, доступность |
| **Доступность / Покрытие** | Календарь доступности по сотруднику; политики минимального покрытия дежурных для групп |
| **Группы** | Группы дежурных + зона ответственности по оборудованию |
| **Сценарии** | No-code редактор графов маршрутизации/эскалации, канал доставки на узле «Уведомить» |
| **SLA** | Нормативы реакции/устранения, автонапоминания |
| **Аналитика** | Операционный дашборд: алерты/инциденты по дням, TrueConf ACK rate + MTTA, Email open/click, SLA, снижение шума |
| **Интеграции / Источники** | Статус каналов доставки (включая живую % доставки по TrueConf/Email) + реестр источников мониторинга с токенами |
| **Аудит / История изменений** | Журнал административных действий; low-code поиск по истории мутаций |

**Пример сценария** (эскалация при отсутствии реакции): узел
**Условие** (приоритет ≥ P1) → **Уведомить** (дежурная группа, первый
доступный) → **Подождать** 10 минут → **Проверка реакции** → если
«нет» → **Уведомить** (руководитель смены). Активный сценарий
исполняется на каждом подходящем алерте автоматически. Живой прогон
и статистика переходов по каждому узлу — на вкладке «Статистика»
внутри карточки сценария. Узел «Уведомить» дополнительно несёт канал
доставки (TrueConf / Email / оба) — параллельная доставка или
эскалация на резервный канал строится обычной веткой графа, без
специального узла.

**Оборудование**: дерево (не список карточек) — раскрывайте филиал,
категорию, объект стрелкой прямо на странице, без перехода на новый
экран; уровни грузятся лениво при первом раскрытии. Поиск находит
объект по имени/id/FQDN/IP на любой глубине и сам раскрывает путь до
него. Клик по названию объекта открывает сводку в панели справа, ссылка
«Открыть полностью» — на карточку с паспортом + KPI + вкладками «Обзор /
Текущие проблемы / Инциденты / История / Граф алертов / Связи /
Изменения». Незакрытый инцидент показывает живую длительность («В
работе, 27 мин»), а не искусственное «Закрыт», пока `closed_at` реально
не выставлен (закрывается, только когда ВСЕ проблемы кластера
разрешены). Граф алертов строится на настоящих `incident_problems`/
`rule_id` (коррелятор), не на визуальном совпадении имён.

**Аналитика**: единые фильтры периода/филиала наверху, KPI-строка,
затем stacked-график алертов (переключатель приоритет/источник),
инциденты по дням + донат состояний, TrueConf (ACK rate, среднее время
подтверждения, эскалации) и Email (open/click — с честной оговоркой,
что открытие письма не 100% точный сигнал) рядом, сравнение каналов
таблицей, SLA-соблюдение, топ оборудования/сценариев и воронка
снижения шума (Raw → Dedup → Incidents → Notifications — события не
теряются, а объединяются).

**Сотрудники**: карточка показывает роль, компетенции, реальную зону
ответственности (из групп, в которых состоит сотрудник), переключатели
каналов TrueConf/Email, подписки и календарь доступности —
типизированные интервалы (`отпуск`/`больничный`/`делегирование`/
`смена`/`на месте` и т.д.) с приоритетом при пересечении, не плоский
статус. Недоступность сотрудника (отпуск/больничный) реально исключает
его из маршрутизации сценариев (`recipient_mode=first_available`) —
не декоративный статус.

## Известный, честно не скрываемый пробел

Reply-ACK на уведомление `NEW` в TrueConf уже работает и используется
сценариями (`ack_check`), но полная семантика отдельных команд бота
`взял`/`не мой`/`следствие` (предложение кандидатов на правило со
симуляцией — раздел 19.1 спецификации, шаг 5) — не реализована; это
явно зафиксировано как следующий этап в [`CLAUDE.md`](../CLAUDE.md) и
[`GO-MIGRATION.md`](GO-MIGRATION.md), не выдаётся за готовое ни в
одном демо-сценарии или на защите. Подробный разбор всех пробелов по
каждому критерию — [`COMPLIANCE_MATRIX.md`](COMPLIANCE_MATRIX.md).
