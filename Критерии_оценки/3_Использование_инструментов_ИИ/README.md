## ADP AI — ассистент поверх данных платформы (новое)

Отдельный модуль, не расширение пайплайна выше: пользователь задаёт
вопрос на естественном языке («покажи активные P0», «кто сейчас
дежурит», «покажи разрывы покрытия») через чат в разделе **ADP AI**
консоли, и получает ответ, построенный из реальных данных БД, а не
придуманный моделью.

**Архитектурное ограничение, которое проверяется буквально:** у LLM нет
прямого доступа к PostgreSQL/ClickHouse/shell. Поток жёсткий:

```
Пользователь → выбор инструмента (Ollama, строгий JSON) → инструмент
из типизированного реестра → проверка права ЭТОГО пользователя →
Use Case → Repository → журнал
```

| Требование | Реализация | Доказательство | Тест (проведён живьём на проде) |
|---|---|---|---|
| Типизированный реестр инструментов | 8 инструментов (`list_active_incidents`, `get_incident`, `find_alerts`, `find_equipment`, `get_available_responders`, `get_coverage`, `get_analytics`, `open_entity`) | `go-platform/internal/adminapi/ai_tools.go` | `go test ./internal/adminapi/... -run TestFindAITool` |
| Каждый инструмент проверяет право именно этого пользователя | `rbac.Grant` того же пользователя, не отдельный AI-грант | `go-platform/internal/adminapi/ai_routes.go::aiChat` | `тестер1` с `deny` на `employees.read` получил `DENIED` от ADP AI на «кто сейчас доступен»; после `grant` — тот же запрос прошёл |
| Реестр переиспользует существующий Query Builder, не строит параллельный | `find_alerts` вызывает тот же `FilterNode`/`compileFilterNode`, что и панель фильтров алертов | `ai_tools.go::aiFindAlerts` | Тот же SQL-путь, что у `/api/alerts` |
| Защита от галлюцинаций (MVP) | Итоговый ответ собирается шаблонно из структурных данных инструмента, LLM только выбирает ЧТО спросить | `ai_tools.go` — комментарий в начале файла | Ответ на «активные P0» при их фактическом отсутствии в БД — «не найдено», не выдумка |
| Структурная навигация, не LLM-URL | `open_entity` возвращает `{type, id}`, маршрут строит фронтенд | `ai_tools.go::aiOpenEntity`, `web/src/pages/AdpAi.tsx::entityHref` | Живой вызов вернул `{"navigate":{"type":"incident","id":"231"}}`, не строку с URL |
| Журнал на каждый запрос + связь с общим Global Audit | Отдельная таблица `ai_journal` (детали: duration_ms/model/explanation) + значимые действия дополнительно пишутся в `change_events` с `actor_type='ai', initiated_by=<пользователь>` | `database/migrations/0021_ai_journal.sql`, `ai_journal.go` | Живая проверка: `change_events` содержит `ADP AI \| ai \| admin1 \| ai.get_available_responders` |
| Деградация при недоступности Ollama | Отдельное сообщение «ADP AI временно недоступен», остальная платформа продолжает работать | `ai_routes.go::aiChat` | Найден и исправлен реальный баг при живой проверке: код путал «Ollama не ответила» с «модель ответила, но не выбрала инструмент» — теперь различает |

**Честно про MVP**: инструменты — только чтение и навигация
(`ai.execute.write` добавлен в модель прав как задел, но ни одного
write-инструмента не реализовано в этой итерации — соответствует
собственной рекомендации ТЗ «MVP должен быть в основном READ +
NAVIGATION»). Кнопка «Почему?» со структурной трассировкой решения
(кто исключён и почему) — не реализована в этой итерации, только текстовая
сводка результата.
