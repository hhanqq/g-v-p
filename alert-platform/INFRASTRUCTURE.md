# Диспетчер — инфраструктура и масштабируемость

Критерий кейса «Инфраструктура и масштабируемость решения» — все цифры
ниже измерены на реальном развёртывании (VM, 90.156.217.61 /
xn--80aebrvrg.xn--p1acf), не оценены на глаз.

## 1. Пропускная способность (измерено вживую, 2026-08-07)

Полный прогон синтетического датасета через реальный шлюз → воркер →
резолвер → коррелятор → приоритизацию → доставку в TrueConf (включая
все 5 ИИ-сценариев, `packages/ai/`, работающие на этом же прогоне):

| Показатель | Значение |
|---|---|
| Объём прогона | 5302 сообщения |
| Приём (шлюз, запись в WORM+очередь) | 225 событий/с |
| Полная обработка конвейером (парсинг → доставка, 1 реплика воркера) | 2095 с на 5302 события ≈ **2,5 события/с** |
| Успешный разбор | 100% (5330/5331 событий; 1 намеренно «грязное» сообщение из синтетики) |
| Резолвинг объекта (не карантин) | 99,9% |
| Доставка уведомлений | 100% (3489/3489) |
| Инцидентов сформировано корреляцией | 112 |
| Средний MTTR | 163,7 с (≈ 2,7 мин, синтетические данные) |

**Целевая нагрузка кейса** — 5400 событий/сутки ≈ 0,0625 события/с в
среднем. Измеренные 2,5 события/с на **одной** реплике воркера дают
запас **более чем в 40 раз** относительно целевой средней нагрузки —
и это с учётом реальных сетевых вызовов к локальной LLM для
классификации/дедупликации, не идеализированный синтетический тест.
Пиковая нагрузка (не среднесуточная) при необходимости покрывается
горизонтальным масштабированием `pipeline-worker` (см. п.3).

## 2. Отказоустойчивость

| Механизм | Реализация |
|---|---|
| Недопущение потери событий | `Signal` — WORM-таблица (раздел И3): запись до разбора, разбор может упасть, событие — никогда |
| Идемпотентность приёма | Уникальность `(source_instance, hash)` — повтор от источника не создаёт дубль |
| Fault-изоляция воркера | Двухфазный `claim`/`process` (`FOR UPDATE SKIP LOCKED`) — ошибка на одном сообщении не топит батч и не роняет процесс (`services/pipeline/worker.py`) |
| Восстановление после краха воркера | `requeue_stuck_processing()` — зависшие `processing`-записи возвращаются в очередь по TTL |
| Надёжность доставки | Исходящая очередь `Notification` (`queued` → `sent`/`failed`) создаётся ДО вызова TrueConf API — раздел 9.8 |
| Деградация ИИ-компонентов | Раздел И5, применено во всех 5 сценариях `packages/ai/`: сбой/таймаут LLM никогда не блокирует конвейер, только убирает необязательное дополнение |
| Резервное копирование БД | Ежедневный `pg_dump` (cron, 03:00, ротация 7 дней) — `~/pg_backup.sh` / `~/pg_restore.sh` на сервере, проверено вживую (пробный бэкап и восстановление отработали) |

**Не реализовано, осознанно** — репликация/failover самого PostgreSQL
(single-instance на демо-стенде) и multi-region — избыточно для пилота
на 87 пользователей (кейс, «пилотный периметр»), кандидат на второй этап
внедрения вместе с расширением на всю группу.

## 3. Масштабируемость

- **pipeline-worker** — горизонтально: несколько реплик безопасно
  конкурируют за очередь (`FOR UPDATE SKIP LOCKED`), проверено логикой
  claim/process, не требует изменений кода для запуска N реплик.
- **Источники** — регистрация нового инстанса через `/sources/` (раздел
  4.3/11.2), подхватывается воркером без перезапуска в течение ~30с.
- **Каналы доставки** — `delivery-trueconf` изолирован от остального
  конвейера через таблицу `Notification`; второй канал — параллельный
  consumer той же очереди, без изменений парсера/корреляции.

## 4. Ресурсы под ИИ-модуль

Ollama развёрнута на том же сервере, что и остальной стек (совместное
использование GPU — демо-масштаб; для продакшена на 87+ пользователей
рекомендуется вынести на отдельный сервер/GPU, раздел «Дополнительные
вводные данные» кейса уже предполагает этот шаг: *«потребует выделения
двух серверов с GPU… увеличит смету»*). Технически ИИ-модуль уже
изолирован программно — все 5 сценариев идут через единый клиент
`packages/ai/client.py`, который можно перенаправить на удалённый Ollama
одной переменной окружения (`OLLAMA_URL`), без изменения кода сценариев.

## 5. Мониторинг и аналитика платформы

`/console/dashboard` (раздел 7 кейса «Аналитика») — нагрузка очереди,
% успешного разбора, % резолвинга, % доставки, число ИИ-дополнений,
открытые проблемы/инциденты, MTTR, задержка обработки; автообновление
15с. `/console/api/metrics` — тот же снимок в JSON для внешних систем
мониторинга самой платформы.

**Живой пример находки через мониторинг**: тот же прогон, что дал цифры
из п.1, выявил при первой версии метрики MTTR аномалию — отрицательное
среднее время восстановления, из-за смешения меток времени двух разных
тестовых сессий в демо-БД (не ошибка конвейера, артефакт демо-данных).
Метрика дашборда защищена от таких строк (`services/api/metrics.py`,
`resolved_at >= opened_at`) — сам факт, что дашборд позволил это
заметить и починить за один проход, и есть демонстрация его пользы.
